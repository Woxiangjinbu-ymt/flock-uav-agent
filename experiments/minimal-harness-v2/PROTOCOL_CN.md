# v2：24 个受控事件的执行协议

本轮授权范围：24 个案例 × applicability/failure 两臂 × 两次重复，共 96 次执行。完整 100 题、13 题旧预算补充、验证集均不启动。初始技能由夹具提交，结论限于“已经正确提交计划”的条件机制，不能验证模型自主选技能的成功率。

## 实现与初态

基础代码逐文件复用 v1 冻结 source.zip；新增 `scripts/harness_v2_*.py` 隔离适配层，原技能、局部修复和强制失效守卫不变。两臂唯一技能调度差别仍是：局部已处理的失败检查点，failure 暂停，applicability 继续。

每次执行使用独立 Python 进程和真实 FastAPI/控制器的进程内 ASGI 接口，模型调用走真实供应商 HTTP。该机制阶段不包括本机 TCP 服务开销，不能直接与 v1 的端到端秒数做因果比较。

完整初态用整个控制器对象图快照恢复，保留实体、位置、电量、目标访问、覆盖、任务和请求历史、无人机私有历史、移动相位、计时器、环境、独立天气与 ID 随机流。公开 Session JSON 作为可读夹具，完整对象图作为恢复依据；先校验文件 SHA，再反序列化可信本地文件并核对结构哈希。每次新建模型上下文、黑板、证据账本和计划；不继承上一题状态。

外生过程按任务相对时间推进。天气及移动目标的 501 秒逐秒事件表提前生成、封存；天气 RNG 与模型/ID 随机流分离。迟到的公开请求按顺序补齐时钟事件，模型延迟可能造成观察时刻不同。当前 24 案例目标静止；另有移动目标相位和天气回放的离线回归。没有声称已制作完整 100 题的独立初态。

## 案例与故障语义

- 8 个可恢复受阻：两种几何初态，各 1、2、4、8 次技能移动受阻。
- 4 个可恢复起飞失败：两种初态及两种受影响 actor，仍有可用 actor。
- 4 个正常成功检查点：四组起飞高度/航向。
- 4 个必须交回：2 个 actor 航向外生变化、2 个第 17 次修复超出既定上限。
- 4 个效果不明：起飞已执行而回执丢失 2 个，未执行而回执丢失 2 个。

受阻通过临时障碍作用于真实控制器，获得真实失败回执和不变的位置；障碍在该动作结束后消退。丢回执分别记录真实动作结果和真实世界状态，不伪造成功、失败或任务进度。故障触发绑定技能调用序号，不绑定模型调用序号或延迟。故障只作用于所测试的技能动作；模型改用原工具绕过后续技能故障属于可观察的接手路径，须报告实际事件暴露数，不能当成该模型已通过所有后续守卫测试。

模型接收真实预提交技能返回的公开状态和 plan_id，共用相同说明模板。checker、完整状态和故障编排不进入模型提示。模型可按 plan_id 恢复，也可使用原工具接手。`needs_replan` 后的恢复尝试、错误 plan_id、无效字段、多工具批次等返回会单独记录。

## 顺序、预算和停止

使用方案种子 20261016。同一案例×重复的 A/F 相邻执行于同一 worker；第二次逐案例反转先后并交换 worker。每次重复内按冻结区组顺序调度，第一次重复全部结束再开始第二次；并发最多两个执行进程。

两臂共享：工具步骤上限 600，图循环上限 1800，时间窗 500 秒，每计划 API 2000、局部修复 16、搜索 16 轮。批量工具可能跨越步骤阈值，记录实际步骤数及停止原因。高上限不意味着已经排除预算影响；触顶保留结果并标注。

准备阶段从初态执行共同公开观测和提交前缀。计时在第一个共同技能检查点开始；没有检查点的未知效果案例在共同观察后的第一次交回开始。该边界之后 applicability 继续执行的技能耗时也计入，不把整段自主执行错误排除为预热。另记共同准备耗时和第一次技能返回耗时。评分时将外生世界推进到 min(实际结束, 500 秒)。供应商在途响应可能超过 500 秒，另记完整模型处理墙钟和实际 HTTP 尝试。超过 630 秒仍不退出的进程保留部分日志后终止，并停止派发。

只保留首次执行，不自动重跑。供应商终止错误、队列/校验错误停止派发，另一已在途执行可结束并封存。SDK HTTP 重试和空响应自动重试在两臂均关闭，并写入配置。累计已报告 token 达 1 亿后不启动新区组，已经开始的区组完成；这是软上限，在途调用可能超出，缺失 usage 不能当作 0 成本。

## 离线验收与在线指标

24 案例做 48 次无模型脚本化执行：核对所有公开调用和回执相同、首次门控符合预期、完整恢复后无历史残留、实际目标结果一致、未知动作不盲重放、修复上限正确。额外回归覆盖移动相位/天气、原始 checker 恢复前后的一致性、真实 LangChain 工具接手和 plan_id 恢复、拒绝日志、独立循环上限、截止时间拦截、冻结范围/哈希校验，以及原 v1 技能和证据回归。

每次执行保存初态哈希、实际公开 API 回执、故障事件、计划/门控日志、部分工具步骤、原生工具链、逻辑模型调用、实际 HTTP 尝试、供应商输入/输出/cache usage、评分就绪耗时、模型处理墙钟、checker 结果及文件封存 SHA。

分析以案例×重复的完整配对为单位，先分别看 12 个可恢复案例和 12 个共享守卫/正常对照，再看案例族；报告成功 W/L、调用/token/耗时配对差。重复不是 48 个独立场景。人工核对真实轨迹的剩余义务、动作效果与最终 checker，不能把 resume、重新进入计划或后续有动作直接算作有效修复。停止或未结束的样本保留，不对未完成分组给总体效果结论。

运行前的 3,000 万–1 亿 token、1–3 小时只是规划区间。前 16 次的 usage 用于校准预算，不据此改任务或参数。96 次全部达到 500 秒且两个 worker 均衡时约 6.7 小时，另加准备、在途响应和封存时间。实际值以日志为准。

全部完成后先给出机制结论和实际 token/耗时，再由用户决定是否启动完整 100 题。

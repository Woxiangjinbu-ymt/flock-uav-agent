# Applicability 与 failure 的受控验证方案

日期：2026-10-16。状态：方案与运行顺序草案已生成，尚未实现 v2 执行适配、制作初态快照或启动模型实验。v1 的实现、冻结材料与结果保持原样。

下一轮重点检验一个具体问题：**当动作失败已经被技能局部处理，且继续执行所需条件仍成立时，继续运行技能是否比交回模型更有效。** 推荐先做 24 个受控事件案例，再做完整 100 题的配对实验，并在预定 13 道适用题上增加循环预算对照。核心方案共 548 次执行，暂估 6.0–10.3 亿累计 token、两个 worker 下 14–25 小时。

## 研究假设与比较边界

当前 `HarnessRuntime._drive` 中，failure 会在 `Checkpoint.failed=True` 时暂停；applicability 在同一局部修复完成后继续。场景变化、动作效果不明、错误回执、修复预算耗尽等强制退出条件，两臂共享。现有 applicability 还不是一个额外训练的失效预测器。

因此本轮分开检验三个命题：

| 命题 | 支持证据 | 反例或不确定结果 |
|---|---|---|
| 可修复失败后的回交有可避免成本 | 同一事件前缀、同一初态下 A 少调用，后续动作有效且满足既定目标 | F 的重新决策更快解决任务；A 持续低效搜索或造成额外失败 |
| 成本改善能转化为完整任务收益 | 完整任务成功率及配对成本同时呈现有利变化 | 只在强制启动技能的案例中有效；主实验效果不清楚或成功率下降 |
| 收益不只来自代理循环上限 | 在较高预算下仍有改善，并记录实际预算余量 | 只有旧低预算下出现优势，或高预算仍触顶导致解释不清 |

A 表示 applicability，F 表示 failure。两臂使用同一模型、温度、提示、工具定义、技能、搜索策略、修复规则和停止条件，只改变上述暂停策略。不同时增加新技能、调整搜索参数、压缩提示或改进接手策略，否则会混入第二项改动。恢复与接手协议的改进另立后续版本。

## 实验组成与执行顺序

| 阶段 | 样本及重复 | 新增执行数 | 用途 |
|---|---|---:|---|
| 离线准备 | 状态恢复、顺序、预算与日志回归 | 0 次模型执行 | 保证对照可解释 |
| 受控事件 | 24 案例 × 2 臂 × 2 重复 | 96 | 隔离门控决策本身 |
| 完整任务主实验 | 原 fast100 全部 100 题 × 2 臂 × 2 重复，使用高预算 | 400 | 自主选择技能后的完整任务结果 |
| 循环预算敏感性 | 原定 13 道适用题 × 2 臂 × 2 重复，补充旧预算 | 52 | 与主实验中相同 13 题的高预算结果配对 |
| 核心合计 | 受控事件与原任务分开统计 | **548** | 本轮建议规模 |
| 可选阶段验证 | validation60 × 2 臂 × 2 重复，高预算 | 240 | 验证向不同场景迁移；不计入核心预算 |

先完成受控事件，检查技术有效性和盲化的成本校准，再进入主实验。前一阶段若揭示实现错误，则停止该版本，保留全部结果，修订后另行冻结；不把挑选出的成功案例继续拼成完整结果。若受控事件没有支持效果，也完整报告；不改案例后继续把它当原假设的验证。

100 题保留原任务文本、检查定义和 605 个检查点。两次重复意味着每臂 200 次任务执行，报告每次完整 100 题结果及预先约定的平均结果，不能挑较好的一次。任务逐题重置后，执行协议已不同于 v1 的整场继承协议，应命名为新协议，不与 v1 分数直接算提升。

`validation60` 与 fast100 按场景不重叠，但仓库文档明确其已参与历史基线和选样，不能称为从未接触的独立测试集。是否扩展到该阶段在核心方案结果和预算清晰后另定；真正的泛化声明仍需新场景或未用于调参的任务。

## 每道任务的共同初态

**完整快照恢复是开跑前的硬条件。** 现有 `Session.reset()` 主要清空统计和历史，没有恢复无人机、目标、障碍和环境实体。仅调用 reset，或在原场景上降落、充电，不能保证初态相同。

快照制作规则如下：

1. 从已有冻结场景 JSON 构造规范初态。保留原任务、实体 ID、坐标、几何条件及原检查；按统一准备流程完成降落和充电，再冻结为每题共同快照。准备过程完全确定，不由 A/F 执行轨迹产生，也不使用某个臂的 `.before.json` 作为主实验初态。
2. 快照覆盖无人机位置、航向、状态、电池，目标访问及覆盖状态，目标运动路径和相位，障碍、天气、任务状态、历史、计时状态与环境随机数状态。检查规范初态确实清除了前题进展，而非只改进度字段。原文件已有的非零状态要明确记录来源，不能暗改成零。
3. 每次执行在隔离的 server/agent 实例中完整恢复快照。对同一题、两臂、两个重复，使用同一快照哈希；每次都重建 memory、blackboard、会话证据索引、计划表与请求历史。模型能通过正常公开工具重新获取信息，不把快照真值、隐藏 checker 或故障标签注入提示。
4. 快照恢复后，执行离线状态比对与统一的公开启动观察比对，记录 `world_state_sha256`、`public_startup_sha256`、`memory_state_sha256`、`source_task_sha256`。仅审计 ID 和绝对墙钟等预先列明的非语义字段可规范化；目标运动相位、位置、访问记录不得为“哈希一致”而删除。
5. 模拟世界以任务开启为相对时间零点。天气等外生随机过程使用独立的、逐题固定的随机流，移动目标从同一相位开始，按预先生成并记录哈希的相对时间事件表推进。A/F 共用同一事件表。模型延迟造成观察时刻不同是实际调度效应，不能要求两臂分叉后的世界状态始终相同。不能简单冻结移动目标而破坏原任务语义。

初态和外生过程在两个重复中不变，以检验模型采样与服务运行波动。未来增加初态种子应成为单独实验维度，不能与本轮的模型重复混为一谈。服务端没有提供采样 seed 时，不能声称两个请求使用了相同模型随机性。

若个别任务明确依赖前置动作，按指令和环境语义制作确定的共同前置脚本，在两个臂运行前冻结。不得按某臂结果补充前置条件或剔除任务。原任务在重置协议下已满足、不可行或语义存疑的情况也保留在分母中并标注。

## 平衡顺序和 worker

实验单位是“任务或案例 × 重复”的小区组。同一组包含 A、F，两臂使用独立恢复的共同初态，在同一 worker 上相邻执行。避免先跑完全部 A 再跑 F。区组内控制条件、区组间随机顺序的依据是 [NIST 随机区组设计](https://www.itl.nist.gov/div898/handbook/pri/section3/pri332.htm)。

运行种子固定为 `20261016`。第一次重复随机分配 AB 或 BA，第二次对每个任务反转为 BA 或 AB，并交换 worker。两个重复各自随机打乱任务区组，最多同时运行两个任务。既平衡先后顺序，也避免每道题固定落在同一 worker。记录真实开始时间、等待时间、模型标识及缓存 usage，不能假设顺序平衡已消除所有供应商波动。

13 道预算敏感性题包含四个条件：A 高预算、F 高预算、A 旧预算、F 旧预算。采用四种顺序轮换，第二次逐题反转。13 不是 4 的倍数，所以周期位置只能近似平衡，偏差最多一个区组；两次重复后每道题的 A/F 先后与预算先后互换。旧预算运行穿插在这些区组中，不能等全部高预算结束后再运行。其余 87 题仅包含高预算的 A/F。

[schedule.proposed.json](./experiments/minimal-harness-v2-plan/schedule.proposed.json) 已列出 548 次执行所属区组、臂、预算、重复和 worker。该文件是可审查的计划，不是已运行日志。正式开跑前应连同执行器和快照整体封存。

## 循环预算控制

| 参数 | 主实验高预算 | 敏感性旧预算 |
|---|---:|---:|
| 任务期限 | 500 秒 | 500 秒 |
| `max_iterations` | 600 | 150 |
| `recursion_limit` | 1,800 | 450 |
| 每计划公开 API 预算 | 2,000 | 2,000 |
| 局部修复预算 | 16 | 16 |
| 搜索最大轮数 | 16 | 16 |

高预算设为旧预算四倍，是预先指定的资源控制值，不是已证明“不会触顶”的数值。当前代码把图循环上限设为 `max_iterations * 3`，同时对工具步骤另行计数；两项必须分别写入配置、运行日志和退出原因。600 不是 600 次模型调用，工具步骤也不等于实际底层 API 动作数。批量工具调用可能跨过计数阈值，须同时记录配置值、触发时计数和实际结束计数。

若高预算仍触顶，该任务保留原结果，报告为循环预算受限，不能从主表删除，也不能临时提高该题上限。此时只能声称“在该预算下的差异”，不能认定已经排除循环预算解释。只有后续另行冻结的更高预算实验才能继续解决这一问题。

预算分析先分别计算两种上限下 A−F 的成功率和调用差，再计算两者的差异，检查门控与预算的交互。13 题样本小，该分析是诊断性证据。主实验不加入 every_step，以集中预算回答 A/F 的差异；不能根据本轮直接重申相对 every_step 的新效果。

## 受控事件案例

这些案例用于验证门控，不计入完整 100 题成功率。使用相同技能代码，在隔离仿真器中以确定的公开工具前缀构造共同计划和证据。技能启动由测试夹具完成，因此只能估计“给定计划已经正确提交”的条件效果；主实验仍由模型自由选择技能。

| 案例族 | 独立案例数 | 构造与预期 |
|---|---:|---|
| 可恢复的受阻候选 | 8 | 两种几何布置，各设置 1、2、4、8 次可处理受阻；不超过原修复预算。A 应继续，F 按原策略暂停 |
| 可恢复的起飞失败 | 4 | 个别 actor 起飞失败后仍有可用 actor；两臂共享禁用与替换规则，区别只在是否回交 |
| 正常成功检查点 | 4 | 适用条件持续成立；两臂都应继续，是阴性对照 |
| 依赖失效或修复耗尽 | 4 | 2 个 actor 状态变化案例、2 个超出修复边界案例；两臂都应转入 needs_replan |
| 动作效果不明 | 4 | 动作已执行但回执丢失 2 例、未执行且回执丢失 2 例；两臂都应观察并交回，不能盲目重放 |

合计 24 个案例，其中前 12 个直接检验当前两臂的差别，后 12 个验证共享行为和失效边界。故障触发绑定到确定的技能步骤或调用序号，不绑定到第几次模型请求或随机墙钟，以免两个臂受到不同扰动。动作效果和回执故障分别记录；仅有 mock 错误而无一致的世界状态，不能作为有效修复案例。

每个案例预先写明允许的局部修复、必须交回条件、剩余目标和独立 checker。离线先验证到第一个分歧检查点之前的公开观察与动作前缀一致；若不一致，该案例是夹具失效，停止该版本，不能用于门控效果结论。重放前缀和预热动作属于测试准备成本，单独计时，不能混入 A/F 后续模型成本。

继续、暂停、needs_replan、STOP 分别记录。评价既包括首次门控选择，也包括后续目标是否完成。仅看到 resume、重新进入计划或发生动作均不足以证明正确恢复。

## 指标与结论规则

完整 100 题的主指标仍为 500 秒任务窗口协议下的完整任务成功率。所有任务、未选择技能的任务、早停、超时和循环耗尽都在分母中。按“逐题重置新协议”报告结果，使用相同原 checker 和截止后的排空、冻结流程；另记截止时仍在途动作及排空期效果，不把排空后通过误写成严格截止前完成。

同时报告配对 W/L、每次重复结果、按场景结果，以及预先固定的 13 道适用题和 87 道非适用题。后者也是解释上的对照：在未提交技能的题中出现的差异，不能直接记为门控收益。不要用“实际调用了技能”的事后子集替代预定适用集合。

成本包括准入窗口内逻辑模型调用、全部实际 HTTP 尝试、输入缓存命中和未命中、输出 token、评分就绪墙钟、模型处理墙钟、工具及公开 API 调用。异常 trace 中可能缺失的 usage 要从请求遥测补齐，不能把缺失当零。报告全部任务的成本以及两臂均成功任务的补充成本，防止快速失败造成虚假加速。

事件层记录：局部失败被处理后的额外交回数，首次交回前的有效进展，错误继续，未处理依赖变化，未知效果动作重放，暂停后的 plan_id/cursor 连续性，对终止计划的无效 resume，以及 needs_replan 后真正达成剩余目标的证据。包装层拒绝、异常退出前 tool_chain 和未完成请求都必须留痕。

预先采用以下解释规则：

- **机制得到支持**：在前 12 个可修复失败案例中，A/F 的事件前缀相同，A 减少回交，保留了有效动作与目标完成；共享失效案例未出现 A 错误继续。报告每例结果和成本，不把零次观察到的错误解释为一般安全保证。
- **具有端到端收益的证据**：高预算完整任务结果同时报告成功率差及成本差，成本降低不是由更多早停或失败造成；按任务配对的不确定性区间支持改善，且两次重复及预算诊断方向一致。若只证明调用更少而成功率区间宽，应明确写“成本改善、任务效果尚不确定”。
- **未证实独立收益**：只在低循环预算下有优势，或只有强制启动案例有效、主实验不确定，或省调用伴随更多任务失败。此时保留 failure 作为强对照，不为了得到正结果而调整语法、阈值或子集。

统计以任务/案例为配对单位，两个重复归入同一个任务簇，不把 200 次执行当作 200 道独立任务，也不把数千个 checkpoint 当独立样本。对成功率差和配对成本做任务级、场景分层的簇重采样，固定分析 seed、10,000 次重采样，报告 95% 区间；同时展示每个重复的 W/L 和原始差异。仅 5 个开发场景，区间不能支撑跨场景总体泛化。零分歧或极少分歧时重采样区间可能退化，不能据此宣称等效或非劣。

上一轮 A/F 只差 1 道题。100 题、两个重复并不保证有能力确认 1 个百分点的成功率差异；本轮主要识别可重复的机制和成本效果，并评估成功率变化。没有预先充分论证的非劣界和样本量，不以“差异不显著”宣布质量无损。结果不清楚时完整收束，后续再设计更多独立任务，不边看结果边追加到显著为止。

## Token 和时间预算

预算基于上一轮 A/F 的完整请求遥测，而非可能不完整的异常 tool_chain。两臂合计 200 次执行实际为 212,765,537 token、2,780 次模型调用、27,555.38 秒评分就绪时间总和。

将两臂各重复两次、暂不考虑协议变化，400 次主实验的基准外推为：

| 项目 | 基准外推 |
|---|---:|
| 累计 total tokens | 425,531,074 |
| 缓存命中输入 | 392,821,716 |
| 未缓存输入 | 22,995,408 |
| 输出 | 9,713,950 |
| 逻辑调用 | 5,560 |
| 两 worker 理想评分工作量 | 7.65 小时 |

逐题重置会去掉“前题已完成目标”的便利，高预算也可能允许更多接手；因此主实验按上述 token 基准的 **1.25–2.0 倍**规划。这是预算情景假设，不是测得的置信区间。时间另预留恢复、进程启动、排空、负载不平衡和服务变化，不能直接用累计秒数除以 2 承诺完成时间。

| 阶段 | 新增执行 | 累计 token 规划区间 | 在线运行时间规划 |
|---|---:|---:|---:|
| 24 个受控事件 | 96 | 0.30–1.00 亿 | 1–3 小时 |
| 100 题高预算主实验 | 400 | 5.32–8.51 亿 | 12–20 小时 |
| 13 题旧预算补充 | 52 | 0.39–0.79 亿 | 1–2 小时 |
| **核心合计** | **548** | **6.01–10.30 亿** | **14–25 小时** |
| 可选 validation60 | 240 | 2.00–3.50 亿 | 6–10 小时 |
| 核心加阶段验证 | 788 | 8.01–13.80 亿 | 20–35 小时 |

13 题旧预算外推使用该子集两臂遥测的重复成本 31,558,620 token，再取 1.25–2.5 倍覆盖初态变化。受控事件和 validation60 是规划预留，尚无相同协议的实测成本。不能直接把 total tokens 都按未缓存输入收费。

建议核心运行预留 **11 亿 token** 的记账预算，并在启动新配对区组前检查已用量与预计剩余成本。按区组暂停时保留未完成清单，不用删题满足预算。受控阶段前 16 次计划内执行可用于盲化的 usage/时长校准，无须额外启动试验，也不据成功率改变案例。

若 548 次执行都占满 500 秒，两个 worker 仅任务窗口工作量就约 **38.1 小时**，还不含启动、排空及服务中断。14–25 小时是正常运行预算，不是最坏上界。离线适配与验证另估 1–2 个工作日；主要不确定项是完整状态恢复和动态世界的可重复推进，不计入在线实验小时数。

## 开跑前的完成条件

下一步先实现隔离的 v2 执行适配，不改 v1 冻结目录。完成以下可检验条件后，才具备正式运行基础：

1. 全部 100 个规范初态制成快照并封存；连续两次恢复的语义状态、公开启动上下文与 memory 初态一致；执行 A 后恢复再执行 B，与新进程恢复 B 的初态一致。
2. 外生天气、目标运动与相对计时可复现；跨任务无 blackboard、历史和 plan_id 污染；动态轨迹没有因规范化时间戳而改变任务含义。
3. 原 checker 在保存快照上的离线判定一致；任务文本、605 个检查点和原定 13 道适用集合校验和不变。新协议的任务准备行为另有版本号。
4. 高/旧两档预算实际生效并分别记录触发原因；未知动作效果不重放、取消、场景切换、修复预算边界和终止计划恢复均通过离线回归。
5. 24 个事件案例的真实初态、公开前缀、故障序号、期望门控及 checker 已冻结。允许不止一种正确接手动作，不按特定模型措辞评分。
6. 保存源码归档、依赖、配置、快照、顺序、指标定义及成本预算哈希；运行时只改变调度臂和预定预算档位。模型服务或基础设施终止性错误停止发新任务并保存证据，不自动补跑；区分基础设施失败、模型任务失败和计划内重复。

目前 [design.proposed.json](./experiments/minimal-harness-v2-plan/design.proposed.json) 与 [case_catalog.proposed.json](./experiments/minimal-harness-v2-plan/case_catalog.proposed.json) 明确标注快照尚未制作，避免把计划清单误认为执行冻结。成本公式及数值在 [budget.json](./experiments/minimal-harness-v2-plan/budget.json)，可通过 [build_plan.py](./experiments/minimal-harness-v2-plan/build_plan.py) 只读读取 v1 证据后重建这些计划产物。该脚本不启动服务、不调用模型。

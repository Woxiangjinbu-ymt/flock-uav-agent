# 模型调用必要性与决策失效审计

日期：2026 年 10 月 15 日。**现有轨迹支持继续研究执行与模型调度解耦，但还不能给出“多少模型调用可以安全删除”的结论。** 明确序列存在连续执行机会；异常处理需要区分局部修复、补充观察和重新决策。最大的架构缺口是没有持久化待执行计划及其适用条件，无法仅凭正常回执判断下一次模型调用是否必要。

## 范围与可信度

审计 R2 fast100 全部 100 题，以及公开搜索对照与处理各 52 题，共 **204 次任务执行、100 个不同 scene/task 组合、5 个场景**。这是已参与开发的历史数据。两组 52 题均属于这 100 题的子集，不能合并为独立泛化样本。

通过 middleware 请求消息哈希的前缀扩展恢复边界，检查跨边界无在途事件，并以工具链和证据注入锚点复核。fast100 的 94 条完整工具链均支持对齐；另外 6 条异常结束轨迹使用仍保留的事件账本。补充集分别有 45、49 条完整工具链。补充集中各有一批工具的实际启动顺序不同于模型列出顺序，批内成员一致，审计不强加批内先后关系。

三组 HTTP 请求数与 middleware 请求数分别都是 1,533、841、777，没有发现同 middleware 索引的额外 HTTP 尝试。**这些是完整轨迹计数，不是严格裁剪到 500 秒的请求数**：旧记录没有逐请求时间。fast100 另有 96 个最后一次模型请求之后的尾部事件，均没有反向归入之前的模型输入。确定性搜索的 746 个事件独立计数。

分类只使用原始指令、当前边界以前的公开回执及哈希边界信息，不使用最终回答、下一步模型动作、最终评分或隐藏检查。规则是探索性制定；不是模型必要性的人工金标准。来源、完整路径和 SHA-256 见 [manifest](manifest.json)，规则见 [审计口径](PROTOCOL_CN.md)。

## 请求边界分类结果

| 分类 | R2 fast100 | 搜索对照 52 题 | 搜索处理 52 题 | 含义 |
|---|---:|---:|---:|---|
| 初始计划 | 100 | 52 | 52 | 保留初始解释与计划 |
| 继续执行候选 | 12 | 8 | 8 | 明确简单序列尚有下一步，已有正确 actor 的成功回执 |
| 转入公开核对候选 | 7 | 5 | 5 | 简单序列回执齐全，可核对终态 |
| 需重新评估相关动作 | 325 | 207 | 158 | 原动作受阻、部分执行、资源或工具能力等假设失效 |
| 先观察或局部修复 | 17 | 7 | 10 | 到达未核实、参数包装或状态冲突 |
| 仍不能判断调用必要性 | 1,072 | 562 | 544 | 没有足够的已承诺计划信息 |
| **合计** | **1,533** | **841** | **777** | 每个请求边界只进一个类别 |

fast100 的 325 个重新评估边界分布在 63 题。一个边界可能含多机、多种异常；若同时有受阻和参数错误，主类别优先重新评估，但保留全部事件标签。不能将 325 解释为“必须调用 LLM 325 次”：技能有已验证的局部修复能力时，可在技能内解决；没有这种能力时才回到模型。它们也不是 325 个独立失败任务。

12 个继续候选来自 7 道完整匹配的“起飞—转向／爬升—悬停”指令，仅要求成功回执和明确剩余动作。这不是已证明的 12 次调用节省，也不能估计更复杂任务的总可省比例。7 个公开核对候选单列，没有把终态核对和最终回答调用全部当成浪费。

原 R2 已经批量调用工具：1,433 个非初始边界中，528 个消费了多个工具回执。后续基线必须保留该能力，不能用“一动作一模型调用”作为虚构的弱基线。

## 哪些事件真正改变下一步

fast100 的 3,342 个已消费工具事件中，记录到 760 次受阻、69 次部分执行、10 次移动完成但到达未核实、10 次参数包装错误、5 次状态冲突、4 次必填参数缺失、2 次电量不足、2 次工具不支持对象类型、2 次查询失败。这是工具层统计；底层导航工具可能包含多次 API 调用。

| 公开证据 | 当时合理的控制选择 | 不能据此做的事 |
|---|---|---|
| 指定机起飞成功，原文明确下一步转向或悬停 | 执行已经确定的下一步，保留逐步回执与中断点 | 为复杂任务凭空推断待执行计划 |
| 路线只完成前缀，后续点受阻 | 保存真实完成前缀；有局部绕障能力则修复，否则重新规划剩余段 | 按提交路线把未执行点记成到达；冻结所有其他 UAV |
| 导航实际移动完成，终点与请求点相差约 1.4 米，到达校验未通过 | 对照任务的坐标／半径语义，做局部距离核对或修正 | 把导航 error 当成完全没动，重走整段；自动放宽任务阈值 |
| `input_json` 应为字符串但收到对象 | 参数本身已明确时做包装修复 | 从完全缺失的参数中自动猜出 actor 或目标 |
| 电量不足、对象类型不被覆盖工具支持 | 调整路线、资源或技能选择；无法解释时交主模型 | 原样重复同一请求 |
| 发现新目标或障碍 | 检查是否影响当前动作依赖与技能可处理范围 | 任何新信息都触发全局重规划 |

当前抽取器在 48 个边界发现当前任务回执中首次出现、且名称与原文相符的目标，其中 8 个还伴随异常。这是信息更新标记；它既不证明计划失效，也不证明原指定 UAV 可以立即合法执行。目标“新”不等于整个场景首次发现。

窄口径下只有 2 个“同 actor、同工具参数、此前受阻且没有记录到成功移动”的重复失败事件。这不足以支持把通用去重／防循环作为当前主贡献，也不排除改参数重试或工具内部的重复行为。

## 真实案例与搜索技能的反例

[案例簿](CASEBOOK_CN.md)给出原始事件和请求索引，包含连续执行、部分路径、电量、未核实到达、参数包装、错误工具类型及重复失败。

最重要的补充证据是搜索处理臂 `5e743d21`：第 434.179 秒公开进度 88% 时运行确定性技能，4.507 秒内执行 240 次移动尝试，其中 236 次成功、4 次受阻，随后公开进度达到 96%。期间产生 746 个公开 API 回执事件，没有为每次移动调用模型。前 3 个受阻事件之后，同一 UAV 还有成功移动；最后一个受阻之后技能达到全局停止条件，该机没有再移动。因此不能写成“四次原目标绕障成功”。

这说明**技能允许处理的异常也可以留在执行层**。简单的“失败即唤醒 LLM”门控会中断已经存在的有效局部处理。但这只是一个实际触发案例，不能将两臂 37/52→43/52 的全部差异归因于门控。后续两题继承 96% 进度，其他差异还受独立模型运行与场景状态影响，详见[已封存在线报告](../r2-public-search-online-20261010/REPORT_CN.md)。

## 对研究路线的决定

1. **保留 harness 主线，先做可观测的计划执行控制。** 主模型提交短计划及 actor、依赖、证据版本、继续条件、可局部修复范围和预算。执行层维护游标，监控器按相关性选择继续执行、补充观察、局部重规划。无计划或无法解释的任务回到现有模型循环。
2. **第一版覆盖两类机制，而不是继续堆模块。** 简单有序动作链验证正确性；现有公开反馈搜索验证较长技能内的状态变化与异常处理。航点剩余段恢复可作为第二阶段，现有 R3 不直接当成已验证收益。LLM 侦察 worker、通用合同解释器和复杂学习门控暂不进入第一版。
3. **新增观测优先于声称节约。** 记录每次计划提交、门控、模型请求起止、技能边界、证据版本、实际影响分支、预算和回退原因，才能在下一轮回答“该调用为何必要”。旧轨迹缺少这些字段，不能靠补写摘要恢复历史事实。
4. **门控与技能分开验证。** 用相同技能、模型和公开信息比较模型逐边界选择、固定步数唤醒、遇失败唤醒、证据适用性门控；各臂共有必要的协议与状态保护。主结果仍是 500 秒内完整任务通过率和 W/L，并同时报告调用、墙钟、token、误继续与不必要唤醒。

完整接口、执行规则、实验分组和停止条件见 [架构与验证方案](HARNESS_AND_VALIDATION_CN.md)。当前可以写的是“审计揭示了控制粒度与证据作用域问题，并提供一个确定性闭环可行案例”；尚不能写“新的自适应 harness 已显著提高性能”。

# R2 总进度题：公开反馈闭环搜索的离线机会与服务端回放

日期：2026-10-09。**判断：障碍回执驱动的动态重选点，在这三道已分析的开发题上形成了真实的几何执行机会；尚不能作为 500 秒在线成功率收益。**按每机最多 16 次尝试，三题的完整闭环分别达到 97%、96%、99% 的服务端进度，原检查器均返回通过。相同题前快照的旧开环回放为 78%、87%、97%。闭环必须执行 397、421、407 次移动尝试并逐次附近感知；目前没有证明 agent 与工具调度能在原 500 秒窗口完成。

## 研究范围与信息隔离

继承[事前固定协议](PROTOCOL_CN.md)及[开环搜索方案](../r2-public-aggregate-search-plan-20261009/REPORT_CN.md)的软搜索范围、70 米候选格点、25 米覆盖评分格点、30 架无人机和每机 16 次机会。首次机群位置、50 米感知半径及 67/78/83 个历史可见障碍来自 R2 原工具回执；三题首次完整感知之前仅有机群枚举、进度和天气查询，没有本题移动。策略只用这些公开输入和随后模拟出的成功/受阻、实际位置、当前位置附近实体回执。它从不读取完整目标坐标、隐藏检查定义或题后快照来选点。

场景真值只进入独立的离线模拟器，负责按冻结服务端规则判定碰撞、耗电、路径到达与 50 米端点感知。远处障碍挡路而当前位置看不到时，策略仅记录该次失败边，不获得障碍形状；当前位置看得到的障碍才加入共享公开地图。新障碍的首次观察动作、无人机和位置均留在[主臂逐次账本](evaluation.json)中，来源核验通过。

三道题原本属于**同一个连续场景**，本轮分别从各自保存的原题前快照独立开始。表中不能相加为一个新的连续场景成绩，也不是与原 R2 的在线配对。

## 原服务端独立回放

用未改动的 FastAPI `TestClient` 把三份原题前快照分别导入隔离进程，按主臂账本依次执行原生 `take_off`、`move_to`、`get_nearby_entities`，在第 4、8、16 轮读取原进度和原任务检查器。三题合计 **1,225 次移动尝试**（1,111 成功、114 受阻）、1,225 次附近查询；逐次移动结果及目标/障碍回执 **1,225/1,225 均与离线模拟相符**。原服务端在碰撞时实际返回 `status=error` 和含障碍名称的错误消息；回放只将这类明确碰撞错误归一为策略的 `blocked`，其他错误不被当作受阻。三题第 4/8/16 轮的服务端进度均与离线值一致，最终原检查器三题均为 `result=true`；第三题第 4 轮 95% 已被原检查器接受，虽未满足题面“超过 95%”。[服务端核对](server-replay-16rounds.json)及[回放脚本](../../../experiments/analysis/validate_closed_loop_server_prefix.py)。

该核对确认了动作、感知和原检查语义，**没有**核对 500 秒在线预算。`TestClient` 没有远程模型等待、部署网络或 agent 调度；执行的是本轮事先生成的端点序列，没有在服务端进程里实时运行选点器。`navigate_to_and_sense` 还含一次内部路径回退，本回放使用原生直线 `move_to` 加附近查询，因此不是原 agent 工具链的同义运行。

## 对论文与下一步的含义

这轮给“**实际回执 → 可见障碍更新 → 重新分配搜索动作 → 原任务进度**”补上了此前缺失的行动机制证据。它比单纯增加证据摘要、再派一名 LLM 观察工人或重复查询整体进度更贴近三题的根因。不过三题已经参与多轮开发审计，且在独立快照中运行；不能把 `3/3` 写成新方法的 benchmark 任务通过率，也不能据此宣称跨场景泛化。

下一步应先把策略压缩为**可中断、可关闭的确定性短技能**：用原公开工具取得回执，每小批次读取公开进度，到达原任务阈值即停止；受阻后更新地图和剩余预算，再选择合法端点。先在隔离本地服务端中按**真实时间**运行，保存每次调用耗时、策略计算时间、模型调用数、动作数、受阻数以及是否在 500 秒内达到阈值，并纳入匹配成功题以检查误触发。若通过，才冻结 R2 与 R2＋搜索技能的同模型、同 500 秒、同场景原序在线配对；主报整题 W/L、回归和成本。此时策略的首个论文主张应是“公开反馈驱动的有界搜索执行”，不要把路径接触、R3 航线监视或额外 LLM Worker 同时混入试验臂。

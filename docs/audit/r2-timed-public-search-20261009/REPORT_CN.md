# R2 总进度题：公开反馈搜索短技能的本地限时验证

日期：2026-10-09。承接[闭环搜索机制审计](../r2-closed-loop-search-20261009/REPORT_CN.md)，按[事前协议](PROTOCOL_CN.md)把策略拆成独立的[纯公开输入规划器](../../../agent4drone/coordinated_search_r2.py)和[限时执行器](../../../experiments/analysis/pilot_timed_public_search.py)。**本轮结论是：三道已用于开发的 R2 超时题，从各自原题前快照启动，真实服务端 API 均可在约 3–6.5 秒内把公开进度推进到题面严格的 96%，原任务检查也通过；但相同题型的成功对照暴露出误触发风险，尚不能接入原 agent 或写成论文主表增益。**

## 执行约束与证据边界

规划器仅接收本轮 `GET /drones` 的机群状态、原 R2 首次完整公开感知留下的障碍黑板，以及本轮 `move_to`、无人机状态和 `nearby` 回执。70 米候选格点、25 米覆盖评分格点、50 米感知半径、机群外扩 200 米、已知障碍 1 米安全缓冲和每机最多 16 轮均沿用上一轮固定策略。每 10 次尝试读取一次公开总进度；读到**严格大于 95%**即停，且每次动作前检查 500 秒墙钟。碰撞仅在服务端明确返回障碍错误时归一为受阻；新发现的障碍共享给后续无人机重新选点。模型调用为 0。

完整 `.before.json` 只用于隔离服务端恢复，不进入策略；原检查器仅在停止后调用。计时从首次公开 API 查询前开始，包含列表、进度、规划、起飞、移动、状态与附近感知；**不包含**快照恢复、先前 R2 已完成的首次全机感知、LLM 规划和 agent 调度。因此这里测的是独立短技能的本地服务开销，不能直接替代原 500 秒 agent 成绩。三题分别从同一原场景的三个历史题前快照**独立**启动，不能合并成一条连续执行的反事实。

## 三题执行结果

| 任务 | 原 R2 题后公开进度 | 本轮起点 | 公开首次查得 >95% 时的尝试数 | 成功/受阻 | TestClient 秒 | 本机 HTTP 秒 | 本轮终点 / 原检查 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| `5e743d21` | 81% | 64% | 370 | 319/51 | 6.638 | **6.312** | 96% / 通过 |
| `24ac1838` | 88% | 81% | 390 | 352/38 | 6.817 | **6.438** | 96% / 通过 |
| `7cdefb56` | 94% | 89% | 170 | 159/11 | 3.047 | **2.945** | 96% / 通过 |

本机 HTTP 是实际 `127.0.0.1` 上独立 Uvicorn 进程的请求，非进程内 mock。三题 HTTP 规划计算分别为 **1.344、1.115、0.470 秒**；其余 API 调用累计分别为 **4.954、5.310、2.468 秒**。最低电量分别为 **82.79%、76.25%、90.66%**。HTTP 与 TestClient 的逐次无人机、目的地、移动结果及停止尝试数完全一致；与此前离线闭环账本的对应前缀也完全一致。先前离线真值账本的最早严格过线时点为第 363/384/167 次；本轮每 10 次查询一次公开进度，故实际停在 370/390/170 次。服务端三题分别返回 32/18/12 个新增公开障碍。

每题均发生 30 次起飞；HTTP 公共 API 调用数按任务依次为 1,179、1,241、559 次，其中每次移动后均读取无人机状态和附近实体。完整逐动作记录与各类 API 耗时见[TestClient 结果](testclient-results.json)和[HTTP 结果](http-results.json)。

## 同题型成功对照：启动门槛还不安全

用相同 R2 fast100 冻结运行中另外三道**题面措辞完全相同**、原检查通过的题作对照。通过原公开任务接口及公开进度接口读取题前状态，再事后联结原检查记录；复算脚本和逐题数据分别见[对照审计脚本](../../../experiments/analysis/audit_public_search_controls.py)、[对照数据](control-audit.json)。

| 原成功题 | 题前公开进度 | “题面匹配且进度尚未 >95%”会触发？ |
| --- | ---: | --- |
| `9c0b52a0` | 100% | 否 |
| `7eba7390` | 100% | 否 |
| `b1ad4f3e` | 85% | **会** |

三道失败题的题前公开进度为 64%、81%、89%，这条朴素规则也都会触发。因而即使给技能加上“未达标才执行”，仍会触碰至少一道原本成功的同题型任务；本轮没有测它对该题的反事实影响。不能用这三个开发失败题的本地成功遮盖成功题回归风险。

## 对论文主线的含义与下一门槛

证据链现为：原 R2 在这类总进度题上超时 → 任务仍缺公开覆盖和实际到达 → 障碍回执可驱动多机重选点 → 短技能按公开进度停止并能在本地原服务端预算内执行。**可写入方法动机与机制验证；不可写为泛化成功率或原 agent 的 W/L 提升。**本地秒数也不是实际飞行时间：服务端命令直接更新模拟状态。

下一步需要先冻结一个**仅依据公开轨迹的触发时机**，对同题型三失败、三成功做 shadow 审计，尤其避免过早接管 `b1ad4f3e` 这类本可自行完成的任务。触发门槛通过后，再在原场景任务顺序下运行同模型、同工具权限、同 500 秒窗口的 R2 与 R2＋技能在线配对，以整题通过数、成功题回归、实际调度时长及 token 为主指标。R3 航线监视、额外 LLM 工人和更宽时间预算应保持为另外的实验条件。

# 新航线验证集：预先固定的生成与配对规则

2026-10-09，模型调用前冻结。本轮是**新任务集上的探索性机制试验**，与原 MultiUAV benchmark 分数分开报告，不替换、删改任何原题。目标是判断：当任务指定的路线确实可以执行时，R3 的剩余航点反馈能否相对 R2 改善原检查和整题通过。

## 队列与选择

- 从固定种子流 `2026100901` 至 `2026100912` 顺序生成候选场景；**只接纳前 2 个通过以下离线规则的候选**，保留每个失败种子及理由，不参考任何 B0/R2/R3 成绩选择场景。若 12 个种子仍不足 2 个，停止并报告，不临时扩充种子。
- 每个场景由本仓库 `RandomSessionGenerator` 生成 2 架无人机、0 个目标、10 个障碍，面积 1000×1000 米；一个新任务规定两架无人机各自从起点经过 10 个航点、抵达终点并落地，飞行高度 26 米。场景 ID、实体 ID、任务 ID由种子确定；任务文本遵循 R3 严格解析语法。
- 路线点由固定的任务采样器选择：相邻航点水平距离 120–330 米，原路线每机水平总长 1,800–3,400 米；用服务端原 `ObstacleController` 在 1 米安全余量下逐段检查，从无人机初始 XY 到起点、10 个中间点及终点均须无碰撞；每个点在任务高度的 1 米余量内合法，终点在地面 1 米余量内可落地。无人机最高高度须高于任务高度。
- 用服务端原 `BatteryConfig` 按所生成天气与每段路线核算，包含起飞和落地，两机各自预计电量消耗不得超过 70%。这只是保守预算筛选，不能代替在线工具试飞。
- 冻结后先进行**零模型调用的服务端试飞**：在独立导入的场景中按指定两条路线执行原生 `take_off`、`move_along_path`、`land`，用未改动的原检查器复核全部检查。试飞在临时服务器副本上进行，不能把试飞后的世界和访问历史带入模型评测。若任一场景试飞失败，记录失败并停止，不在看到结果后替换种子或修任务。

## 在线配对

- 每个接纳场景只有这 1 道题。R2 与 R2＋R3 各从**相同冻结的原始场景 JSON**启动独立服务和空 blackboard；同模型、同工具、同依赖、原检查器、500 秒窗口。R3 仅多航线证据模块和反馈，观察工人关闭。
- 每臂每场景只计首次可评分尝试；端口绑定等零评分部署失败必须保留记录且不算模型重试。场景顺序按固定种子升序；臂顺序第一场景 R2→R3、第二场景 R3→R2，以减少固定运行次序的偏差。两臂的模型随机采样无法保证相同动作。
- 主指标：每场景整题通过、访问/终点/落地原叶检查通过；机制指标：R3 解析与提示出现、首个漏点是否取得指定无人机真实成功回执及原检查；成本指标：任务耗时、模型调用、tokens、超时。报告每题 2×2 原始结果，不挑只对 R3 有利的任务。
- 这 2 个新场景仅验证机制可行性，不能单独估计泛化增益。若 R2 两题也都通过，报告“没有可救回对照失败”，不把 R3 同样通过记成增益；若 R3 失败，也原样报告。

## 实验边界

离线生成器与可行性门槛是研究者新加的**验证集构造规则**，不是原 benchmark 或 agent 的能力。官方 1,500 题结果保留；新任务集单独命名、冻结和评分。几何、试飞和电量检查只保证存在一条可执行路线，不能预言 LLM 会在 500 秒内找到它。候选内容和种子生成前已固定；检验后不得按模型得分更换题目。

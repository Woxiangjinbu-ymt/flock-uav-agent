## 准备输入与冻结顺序

| 任务 | 依赖 | 操作 | 验证 |
| --- | --- | --- | --- |
| T01 核对请求来源 | 无 | 在 `prepare` 校验索引与原 campaign 的固定哈希。对每个 `slot_id + turn` 检查 worker 封存，按原始 HTTP body 字节的 SHA-256 唯一定位请求。核对思考开关、种子和 `spent_before`。 | 50 个决策位置各匹配一条请求，覆盖 28 道题，思考开/关 27/23。用摘要错误和重复匹配各验证一次准备失败。 |
| T02 重现历史 A | T01 | 保留原消息、历史思考、工具数组及各对象的字段顺序。用冻结 tokenizer 和模板重新渲染 A，用同一解析器重放原始生成 ID，对照旧记录的整组解析与停因，核对 4 条合法感知的公开回执。 | 50/50 条 A 的输入 ID 与原记录逐个相同；原分组复得缺参 42、字段展平 4、有回执 4。 |
| T03 核验 B 的唯一改动 | T02 | 深拷贝 A 的公开请求，仅按技术方案的固定文本替换目标工具的描述末尾。逐路径及顺序比较两侧，再用各自输入长度和原轮预算计算输出上限。 | A/B 完整描述摘要与方案相同。50 条 B 均多 48 个输入 token，两侧输出上限均为 2,048。修改第二个字段或调换工具顺序时，准备阶段须报错。 |
| T04 写入配对清单 | T03 | 按索引原顺序生成 100 个槽，以 `slot_id + turn + 条件` 为唯一标识。奇数行先 A，偶数行先 B。封存顺序、种子、来源和输入 ID 摘要、预算、说明与依赖摘要。 | 得到 25 对 A→B、25 对 B→A，所有槽唯一且成对。再次从原归档准备，清单有效内容与摘要相同。 |

## 单轮运行、故障恢复与卡时

| 任务 | 依赖 | 操作 | 验证 |
| --- | --- | --- | --- |
| T05 封装公开请求 | T04 | `run` 从冻结清单载入历史，调用原 `StudentProcess.request`。两侧分别用原种子和已耗 token，同一模型常驻，按每条请求的实际输入限长。从当前单调时钟重建回合截止，按原位置足够的余时保留完整的 120 秒请求时限。将历史结果标签、私有检查与仿真器留在推理接口之外。 | CPU 替身捕获 A/B 两次调用，核对历史、工具、思考状态、种子、上下文与输出限制；历史标签和私有状态均未进入消息。模型生成的调用只交给解析器。 |
| T06 记录槽与回执 | T05 | 加锁后领取槽，再派发请求，先原子写入原始回执，再提交槽终态。写入输入/输出 ID、EOS、整组解析、token、时延、显存与服务身份。恢复时核对准备清单、模型和运行代码的摘要。 | 在派发后及回执落盘后分别中断。前者如无回执且派发状态不明，记缺测；后者从回执补记。模拟重复启动，两次合计每槽最多一次派发。摘要不一致时阻止续跑。 |
| T07 执行独立预算 | T04 | — | 可控时钟夹具在余额仅够一次请求及收尾时允许派发；少 1 秒即停止。用只够请求却不够重载的夹具验证停线，保留未启动行。 |
| T08 核验取消与续跑 | T06、T07 | 健康服务请求超时后取消并关闭进程；下一槽按预算重载相同环境。区分协议超时、服务故障、缺测和未启动，保存真实可见的用量。 | CPU 替身依次模拟超时与丢失响应。确认超时槽只尝试一次、丢失响应单列缺测；无法观测的 token 标为未知。 |

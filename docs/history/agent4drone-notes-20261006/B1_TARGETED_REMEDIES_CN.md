# B1：按失败类别做局部补救

日期：2026-10-06。分支：`codex/b1-targeted-remedies`。版本标签：`b1-targeted-remedies-v1`。

本轮以 B1（`b1-navigation-contract-v1`）的执行代码为起点，依据[原版失败重审](../../results/b0-failure-reassessment-20261006/REPORT_CN.md)做小改动。目标只有任务成功率；调用数、token 和完成标志的严格程度都不代替外部任务通过率。B1 本身相对 B0 的总体收益仍未证实，本轮也不预先声称有收益。

## 1. 分类与本轮处理范围

下表是有轨迹依据的机制分类，不是全部失败的互斥归因统计。同一任务可能有多个原因；消除一个局部错误也不保证整题成功。

| 类别 | 已核对案例（scene/task） | 本轮补救 | 仍未解决的部分 |
|---|---|---|---|
| 最终间距被当成移动长度；手算坐标略超上限 | `fb8971ec/82077301`、`04cd6269/0cb39a4a` | 新增可选 `move_within_distance`，根据当前两机位置计算并执行接近动作 | 模型是否选用；参考机继续移动；最短接近点被障碍挡住时的其他可行接近点 |
| target_id 与 coverage_plan_id 混用 | `ef36e27a/4ccc9027` | 覆盖计划给出完整可调用参数；错误回执附本次工具实例、对应无人机的候选计划 | 模型是否选择正确目标；尚未发现的目标不能靠句柄纠错得到 |

## 2. 间距补救：替模型完成参数计算和执行

注册工具从 29 个增加到 30 个，仅新增 `move_within_distance`。例如用户要求把 Drone A 移至距 Drone B 不超过 19 米：

```json
{"drone_id":"resolved-a-id","reference_drone_id":"resolved-b-id","max_distance":19}
```

该对象作为原工具协议的 `input_json` 字符串传入。工具读取两机当前位置，计算应该移动到哪里，然后调用原有 B1 导航。它不把 19 米当成“再飞 19 米”。

- 默认读取公开会话的 `is_distance_3d`：False 为 XY，True 为 XYZ；用户明确要求时可传 `distance_mode=2d/3d`。这不是隐藏任务 checker，也不读取目标全集或判题进度。
- 默认保持移动机的当前高度；可用显式 `z` 指定高度。不会自动起飞或移动参考机。
- 目的地略放在用户上限内，数值余量至多 0.1 米，并使用比余量小的导航容差，避免 1 米导航容差吞掉 19.012→19 这种短距离纠偏。这是执行用户给定上限的计算，不是调整 benchmark 阈值。
- 3D 模式中高度差恰等于上限时没有内侧余量，工具尝试移动至参考机的 XY，再按实际位置报告距离关系。
- 当前已满足距离关系时无需再飞。3D 模式在所选高度不可满足时，说明高度限制及下一步选择，不宣布整题不可完成。
- 复用 B1 的一次直接移动及遇空间阻挡时的一次规划回退。结束后重新读取两机位置，分别返回距离是否满足及导航回执；不自动循环追赶。
- 顶层 `success` / `within_distance` 只表示当前观测的间距关系。即使原路径只执行了一部分，只要用户要求的间距已满足，就不为完成工具自选的端点再要求移动；`navigation_result` 中的部分执行、阻挡或未知回执原样保留。这不表示用户的其他任务也已完成。

两机状态是先后读取的观测，不是同时采样的持续编队保证。工具只提供接近动作，后续任务仍由原模型工具循环执行。更复杂的环形可达点选择留待有新失败证据时处理。

## 3. 覆盖句柄补救：让现成计划容易执行、填错后容易继续

`generate_coverage_path` 的每个无人机分配项新增 `execution_call`，包含真实的 `tool` 名称及 `arguments.input_json` 字符串。模型可以直接复制下一次调用，无须重新拼接计划 ID。

两个路径执行工具遇到不存在的计划句柄、或计划里没有该无人机时，返回：原错误、请求的句柄与无人机、候选目标名称/ID、精确的纠正调用参数。候选只来自当前 `create_uav_tools` 实例生成、且包含该无人机路径的计划。多个候选一并展示，由模型按任务目标选择；工具不自动换目标或执行。

旧全局缓存和已知有效句柄的执行行为保留。本轮只限制错误提示的候选来源，不把缓存改成新的任务状态系统，也不宣称已实现完整跨会话缓存隔离。显式航点、原有 partial 默认值及成功回执保持原行为。

## 4. 执行提示与边界

提示仅补充表中几种具体操作：距离关系、方向航段、当前位置拍照、精确目标名、已发现与全部的区别、及时执行与收尾。它们帮助模型选择下一动作，不是运行时拒绝条件。

拍照 API 没有返回被摄目标名单。局部 `nearby` 对圆形/多边形目标采用形状距离，也不能直接作为照片包含目标的保证。因此本轮没有新增照片认证、推断的 `captured_targets` 或拍照门禁。

单模型循环、session 黑板、终止标记、运行预算、原判题、原导航算法均保持 B1 行为；不新增 Planner、任务合同、Memory 层或全任务验证器。原来的移动、拍照、起飞、降落工具照常可用。新增工具在可用工具集合中明确标记为方法变化。

## 5. 验证与下一步判断

本轮做离线确定性验证：真实失败中的距离几何、短纠偏、2D/3D 及高度、阻挡/部分移动/参考机改变、覆盖句柄误填后的纠正调用、原调用兼容，以及真实 FastAPI 回执接入 B1 导航。集成测试使用临时子进程和 TestClient，不启动模型或付费实验。

最终验证：**299 passed，3 个既有 warning，无失败、无跳过**。其中本轮新增 35 个距离工具用例、10 个覆盖调用用例、4 个真实服务场景；真实服务集成合计 9 例通过。warning 为 Starlette/AnyIO 弃用提示及 Agg 非交互绘图提示。`git diff --check` 通过。执行命令（在 `agent4drone` 下）：

```sh
MPLBACKEND=Agg LANGCHAIN_TRACING_V2=false LANGSMITH_TRACING=false .venv/bin/python -m pytest tests -q
```

额外覆盖了“路径部分执行但实际间距已经满足”的情形：关系成功正常返回，原始导航状态仍保留；以及动作后观测失败时不伪造距离、保留回执且不自动重试。离线通过仅说明工具行为符合预期，不等于模型会选用，也不等于总体成功率提升。

之后若做成功率实验，仍需保留 B0、B1 参照，分开评估“间距工具”“覆盖提示”“执行提示”的影响；同模型、同预算、同题序并保留成功侧回归检查。诊断过的任务可用于机制复核，但不能作为唯一泛化证据。失败、不支持及未执行仍保留分母，不能靠更严格的内部判断或挑选任务制造提升。

# Agent4Drone 两模型失败分析与未来两周工作计划

分析快照：**2026-10-05 09:35:44（北京时间）**。这是正在进行的 Qwen 全量实验的中期分析，不是 Qwen 最终成绩。

本轮结论：优先研究**有执行证据的任务闭环、面向部分可观测环境的搜索、考虑剩余预算的执行调度**。同时先独立修正已被实际轨迹证实的导航接口问题，并把任务可满足性问题列为单独审计对象。单纯换模型、增加提示词或延长时间，无法解释和解决当前全部失败。

## 1. 数据范围与口径

- DeepSeek：`20261003-143255-full-5c501118`，官方 `deepseek-flash`，75 场景、1500 任务，使用已选定的有效场景版本。
- Qwen：`20261004-142512-full-aca112a7`，`qwen3.8-flash`，本快照只纳入 64 个已完成封存场景、1280 任务；其他 11 场景、220 任务不计入本次模型比较。运行中即使已有部分题得分，也不拼入统计。
- 对这 64 个场景，取 DeepSeek 对应的同一批任务作配对对照。两模型对应指令与检查树逐条一致。
- 共对 **2780 条任务**重放保存的原检查响应，校验所用文件的封存哈希；对 **429 条失败执行记录**做工具轨迹、局部黑板、检查响应和原场景几何的离线审计。下文详细分析代表案例，自动信号不冒充逐条人工根因结论。
- 只读原运行证据，没有调用模型、连接运行服务或重跑实验。当前相关 Agent/Server 源码与两轮冻结版本匹配；Qwen 冻结源码总清单保持一致。
- 分析校验的是实际消费的证据文件，不声称重新校验了运行目录内所有文件。证据哈希见 [evidence-sha256.json](evidence-sha256.json)。

**任务成功**以完整检查树为准；“差一个 check”主表指任务失败、至少一项通过且恰好一项叶子检查失败；“零通过”指所有叶子检查失败。单检查任务失败放入零通过组，以免重复计数。如果按“恰好一项失败叶子”机械计数，DeepSeek 全量是 **111 条 = 91 条部分成功 + 20 条单检查零通过**，Qwen 当前是 **99 条 = 85 + 14**。

历史供应商欠费、被替换的 generation 不属于模型能力失败。本次配对场景的遥测没有终止性供应商错误。超时是 500 秒任务预算耗尽后的状态评分，不等于零通过；日志中的 `cancelled by user` 可由 runner 的截止取消触发，不能据此认定人为取消。

## 3. “差一个 check”：先分清可修复收尾与任务约束问题

| 唯一失败检查 | DeepSeek 全量 | DeepSeek 配对 | Qwen 配对 |
|---|---:|---:|---:|
| 航点历史访问 | 32 | 27 | 27 |
| 指定目标到达，任意无人机 | 16 | 11 | 19 |
| 指定无人机到达指定目标 | 8 | 4 | 15 |
| 定向移动距离 | 14 | 12 | 4 |
| 双机距离 | 13 | 12 | 7 |
| 指定目标出现在照片中 | 4 | 2 | 6 |
| 区域覆盖比例 | 2 | 1 | 3 |
| 起飞历史阈值 | 2 | 2 | 2 |
| 降落历史 / 当前着地 | 0 | 0 | 2 |
| 合计 | 91 | 71 | 85 |

**A. 部分“近成功”实际存在硬几何冲突。** 用原仿真 `Obstacle.to_geometry()` 离线计算，仅标记“目标点到障碍边界的距离大于检查容差，且障碍 height=0”的保守证据。DeepSeek 全量 63 条失败任务、Qwen 当前 41 条失败任务至少包含一项这样的失败坐标检查；其中差一项组分别为 **30/91、23/85**。这些标记均不涉及 OR 检查树。该判据是充分的局部不可达证据，不是完整的任务可满足性检测；未标记的任务不保证可解。

例：`cc05a425/25d30560`，两模型均为 3/4。要求经过 `(288,205,16)`，圆障碍中心 `(288,181)`、半径 41、height=0；点位深入障碍约 17 米，而检查容差只有 3 米。两者都绕到安全点后继续下一航点。应把“不可达且已说明”与“忘记航点”分开；不能把学会进入障碍当作算法收益。

**B. 指令与隐藏阈值不一致。** `c350908c/f30cc643` 要求起飞到 1 米，起飞检查却固定 `min_altitude=5`；两模型都按 1 米执行，得到 3/4。另有 `056a1f86/077f83b6` 同型案例。应修订任务生成或另列一致性审计，不应将隐藏的 5 米阈值塞进 Agent 提示词。这里是规格不一致，不声称逻辑上绝对无法用额外动作满足。

**C. 严格边界与数字计算缺少余量。** `fb8971ec/82077301`：DeepSeek 把两机停在自认为相距 19 米的位置，实际检查为 **19.012 > 19**，2/3；Qwen 同题为 **194.378 > 19**，把“最终距离上限”执行成了“靠近移动 19 米”。前者需要基于当前坐标的确定性计算和边界余量，后者需要明确区分动作距离与终态距离。DeepSeek 13 条双机距离近失败中，有 7 条检查响应值只超过阈值 0.012 米以内或因显示舍入看似相等；这是数值边界候选，不把舍入后的相等值当作精确证明。

**D. 漏最后一个动作，确实是高价值修复对象。** Qwen `35ce64d8/cf8ee51f` 为 **38/39**：三机长航线已完成，API 记录只有两次 land，第三架仍在 27 米悬停时耗尽预算。DeepSeek 同题 39/39。适合为“航线执行→确认位置→降落”预留完整动作包预算，并在截止前优先收尾。

**E. 定向里程被净位移替代。** Qwen `4e425a5b/4cb91745` 为 15/16：最后报告南向净位移 55 米，但检查要求“航向在指定容差内的实际移动段累计长度”，该方向累计值为 0。绕障斜线的南北分量不能直接代替指定航向的航段。需要按航段记录方向、长度和未完成的剩余量。DeepSeek 也有 14 条定向距离近失败；其中还混有接近数值阈值的情况，不能归为同一种规划错误。

**F. 经过目标、到达目标、拍到目标并不等价。** Qwen `93831d6d/7af66f50` 为 3/4：移动过程触发了 Circle Target 1 的到达记录，但第一次拍照时位于 `(150,480)`，目标中心 `(209,650)`，相距约 180 米，超过 50 米摄影检查半径。照片 API 成功只证明拍照动作发生。应让拍摄技能携带目标 ID、拍摄位姿和目标可见性证据，必要时先靠近再拍。

**G. 未发现目标成为最后的缺口。** `76802002/55b61526` 两者均 2/3；DeepSeek 长搜索后称 Waypoint 1 不存在，Qwen 搜索到超时。原场景中的 Waypoint 1 明确存在于 `(844,79)`。对所有失败检查涉及的目标 ID，本轮没有发现任何一个缺失于原始场景。黑板没有它，不等于世界里没有它。

因此，不能把 91 或 85 条全计为下一轮可获得的成功增量。仅扣除已证实的几何冲突与两条起飞规格不一致，剩下的是 **59 条 / 60 条待进一步验证的近失败候选**，不是承诺可修复的任务数。

## 5. 结合 Agent4Drone 架构：现有闭环的薄弱环节

当前实现以一个 LangChain `create_agent` 运行时调度多无人机工具；无人机数量不等于独立 LLM agent 数量。感知黑板按 session 共享，工具层包含点导航和覆盖规划。论文式观察—规划—执行—验证流程，在代码中相当一部分仍靠模型自主遵循 prompt。

| 架构环节 | 本轮证据 | 建议改动 |
|---|---|---|
| 工具返回与导航 | Server 主要返回 `status`，导航却判定 `success`；已到达也返回失败；受阻时可能跳过 fallback | 统一动作结果为 completed/partial/blocked/error，保存已完成航点、当前位置与原因；修复导航成功判定和受阻分支 |
| 任务理解与实体解析 | Drone 20→Drone 18、Circle Target 2→Circle Target 1、target_id→plan_id | 建立结构化任务条件与实体表；执行前确定性校验 name↔id、entity type、plan handle，禁止静默替换对象 |
| 黑板与搜索 | 把未发现当不存在，把已发现数量当全球分母 | 黑板区分事实、推断、未知；记录观测时刻、来源无人机、搜索覆盖范围；用候选区域/覆盖地图指导下一次感知 |
| 导航与覆盖执行 | 障碍内终点、partial path、长路线预算耗尽 | 小批次执行、按新感知重规划、进展检测与限次恢复；覆盖规划把障碍和实际已覆盖区域纳入规划 |
| 验证与终止 | 19.012 米、照片不含目标、38/39 未降落；带结束标记的失败仍 success=True | 用动作证据更新任务条件账本；完成态必须有证据，unsupported/blocked/partial 独立返回；只对未满足条件做局部修复 |
| 时间与资源 | Qwen 145 次超时，长尾调用达数百秒；长航线还会耗尽电池 | 同时管理剩余秒数、动作包成本和电量余量；减少冗余读状态，提前为着地等必做动作留预算 |

### 已证实的导航接口问题，应先单独修复

`uav_langchain_tools.py:356` 的 `_navigate_to_destination` 用 `direct_result.get("success") is True` 判成功；API Client 没有把 `status` 归一化。`_move_result_indicates_failure` 也要求 `success is False`，所以实际的 `status:error` 可能进不了路径规划分支。

本轮在**失败任务的可用 tool_chain**中，发现 DeepSeek 115 条任务、1257 次调用，Qwen 59 条任务、299 次调用，存在“`success=false` 且 `distance_remaining=0`”。超时轨迹常保留 API 调用但丢失 tool_chain，因此这些是可观测子集计数；它们证明工具反馈有问题，**不证明修复后这些任务全部能通过**。

无服务调用的隔离探针复现了三种情况：`status:success` 且到达时仍报失败；`status:error` 时没有调用感知/规划路径；同 XY、错误高度却直接返回成功。见 [navigation-contract-probe.json](navigation-contract-probe.json)。本次只分析，尚未修改生产实现。

### 验证器的权限边界

在线 Agent 的验证依据应来自**原始自然语言指令、允许的局部观测和自己的动作回执**。本报告使用隐藏检查、完整场景和几何信息仅作离线诊断；不得把这些信息回流到在线 Agent。

例如双机距离可由允许查询到的当前坐标计算，ID 可由 list_drones 校验，拍照可记录目标与拍摄位置；但 Agent 不应直接读取隐藏 `/check/*` 或完整目标列表以追求分数。全局任务进度若当前权限不可观测，应明确承认不确定性。若增加一个公开进度反馈接口，应作为另一个观测设置单独实验。

黑板目前主要存 targets/obstacles/drones、facts 和自由文本 notes；虽然有 `_step`，实体记录中并未保存该次观测的时间/来源。它也没有独立的“已执行且已验证的任务条件”列表。因此，应新增的核心是**证据驱动的执行状态**，而不是扩大自由文本记忆。

## 6. 接下来一至两周：交付、顺序和验证

建议主目标：在相同权限、500 秒预算和原场景执行协议下，提升可执行任务的完整完成率，重点降低“已做大部分却漏一个条件”及“搜索/绑定/早停导致零通过”，并对不可达任务给出正确诊断。

| 阶段 | 建议时间 | 交付物 | 验证标准 |
|---|---|---|---|
| P0 证据与任务审计 | 第 1–2 天 | Qwen 完成后的最终配对表；近失败/零通过样本集；几何冲突、阈值不一致、未知目标分开标注 | 完整分母与原检查重算一致；每个根因标签可追溯到指令、API、状态或源码；不使用模型自述作为唯一证据 |
| P0 工具修复 baseline | 第 2–4 天 | status 归一化、导航 XYZ 判定、部分路径回执；实体和 plan handle 校验 | 已到达误报与同 XY 错高度探针通过；blocked 能进入预期恢复；不把 partial 当 completed；与原 baseline 单列结果 |
| P1 完成条件与局部修复 | 第 4–7 天 | 结构化任务条件、动作证据账本、终止状态；距离计算、照片有效性、定向里程、降落收尾技能 | 可修复近失败组优于修复 baseline；早停/错绑定减少；原成功任务有回归监测；不读取隐藏检查 |
| P1 搜索与预算管理 | 第 7–10 天 | 感知覆盖地图、未知区域队列、来源/时效标记、无进展退出规则、预算与电量预留 | 未发现目标造成的失败和超时下降；收尾完成率提高；报告调用数和延迟，而不只报告分数 |
| 收敛与对照 | 第 10–14 天 | 小规模消融、两模型整场对照、最终报告 | 相同权限/预算/并发；报告收益与回归、任务族分布、场景层面不确定性；收益不足的模块不进入主方法 |

**若只有一周：完成任务审计、工具修复 baseline 和完成条件闭环。** 搜索/预算先保留最小版本，避免同时改太多模块而无法解释收益。暂不把多 LLM 分工、强化学习或大幅改写系统 prompt 作为首轮主线。

建议按以下消融组织研究：`B0 原 Agent4Drone → B1 工具修复 → B1+V 条件验证/局部修复 → B1+S 搜索与预算 → B1+V+S`。先在固定小场景集筛选，随后在预先选定的其余场景验证；两个模型都要对照。可以把“近失败候选解决率 ≥30%、零通过与超时不恶化”作为开发门槛，**这是目标，不是由当前数据预测的收益**。

最终至少报告 Task Pass、Avg Check、Global Check、零通过（单检查/多检查分开）、近失败转成功率、超时率、错误完成声明、LLM/API 调用数和延迟。候选组提升必须同时看原成功任务的损失。

方法比较应整场重放，保持场景内 20 条任务的顺序、准备步骤和共享黑板策略。两模型配对的是相同任务，不代表每题开局世界状态完全相同：前题位置、覆盖记录和记忆可能已不同。直接抽出单题重新初始化会改变问题。单题恢复仅用于固定快照上的诊断实验，并单独标识。

开发失败集上的收益不等于泛化收益；当前仅单轮模型结果，也不足以宣布稳定优劣。最终以场景为统计单位做配对分析，预算允许时重复关键场景。保持原 benchmark 的完整分母成绩，同时另报预先定义的可满足性审计分层，不能事后删除难题美化主成绩。

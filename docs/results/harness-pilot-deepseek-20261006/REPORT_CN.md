## 3. 相比原版和 B1，到底增加了什么

B0 的主要执行路径是“读指令 → 模型选择工具 → 根据回执继续行动”。B1 保持原有 Agent 循环，主要修正导航、服务端命令状态与工具回执的一致性，避免把 blocked、partial、降落后的导航等情况误报为成功。

新 Harness 在 B1 上替换了控制循环，增加如下机制：

| 新增机制 | 原本目的 | 本次观察到的失败方式 |
|---|---|---|
| 指令编译成 TaskContract，再由模型 review | 固定目标、顺序、实体和完成条件 | 接受运行时不认识的谓词/参数，然后冻结错误合同 |
| 短计划及 condition_ids、requires、depends_on | 让动作与任务条件可追踪 | 把动作将产生的结果变成执行前必须成立的前置 |
| WorldMemory、事件证据和条件状态机 | 区分旧观测、真实状态、已完成事件 | 已读到正确高度仍因错误谓词判 unknown；证据过期与状态破坏混淆 |
| 证据缺口决策与单焦点局部修复 | 优先解决阻碍完成的缺口 | 正常多机行动被限制为某一个条件链的“修复” |
| 计划范围检查、保护条件、恢复义务 | 防止无关行动破坏已完成目标 | 后面的一个步骤被拒，合法的前缀也不能执行；等高度移动被要求恢复高度 |
| unsupported 与严格完成判定 | 不虚假宣称不可验证的目标完成 | 无法证明的任务语义成为下游硬门槛，合法后续动作被阻断 |
| 连续无效计划终止、独立编译/审查预算 | 避免无限循环 | 重复遭遇固定合同错误，三次拒绝后退出，没有合同修订或降级出口 |

```mermaid
flowchart LR
    A[用户指令] --> B[模型编译与审查合同]
    B --> C[固定合同]
    C --> D[条件与证据判定]
    D --> E[前置条件和修复范围门控]
    E --> F[工具执行]
    F --> G[新观测与 Memory]
    G --> D
    C -. 词汇错误不能由新观测修正 .-> D
```

这条闭环在“合同正确且覆盖任务语义”的理想输入下可以工作；实际模型输入没有满足该假设。运行时却把自身解释失败当成世界证据不足，形成无法靠行动修复的循环。

## 4. 导致下降的首要原因及证据

### 4.1 接口没有真正类型化：错误合同先通过，执行时才永久 unknown

`predicate` 是任意字符串，`params` 是任意字典。编译提示出现 `state altitude`，判定器只认识 `altitude`；合同校验检查了引用和 DAG，却没有检查谓词及参数是否能执行。10 份已安装合同中 **7 份出现了这种不被识别的谓词名**。

旋转题 `b1eb0270` 已起飞到 14 米，状态查询和外部高度检查都证实到位，但合同写的是 `state altitude`。高度条件一直 unknown，后续旋转 353° 被拒绝。B1 同题通过。`91e5a616` 还出现 `action_completed` 附带不支持参数，以及合同 `takeoff` 与事件 `take_off` 命名不一致。

这是确定性的接口缺陷，应在模型输出进入系统时被识别、解释或拒绝并修复。让模型再观察、再规划、再花预算均不能把错误词汇变成合法词汇。

### 4.2 前置与后置混用：要求先起飞，才允许起飞

配送题 `6294fe84` 的起飞步骤关联“起飞事件”和“起飞后高度”两个条件；后者依赖前者。执行器把两者的依赖统一提前检查，于是要求起飞事件在调用起飞之前已经完成。三次提案被拒，**整题零动作**，B1 同题通过。

合同的 DAG 无环，不代表映射到执行步骤后没有自锁。必须区分动作前提、动作效果与任务顺序，不能从“我要推进哪些条件”直接推导“这些条件的依赖都必须在动作前满足”。

### 4.3 用单焦点修复管所有执行：多 UAV 的独立行动被判越界

双机编队题 `fa30ebff` 中，当前焦点属于 Drone 19，模型同时计划 Drone 6 起飞。Drone 6 的动作被判超出修复范围，整份计划拒绝，Drone 19 的起飞也未发生。

这类范围规则不是物理安全约束，而是调度选择。把所有正常规划都套进局部修复范围，限制了多机任务的合理行动。该题 B1 也失败，不能称为新增回归，但它直接证明新版额外引入了执行阻塞。

### 4.4 把不能证明当成不能行动：unsupported 扩散到后续动作

通信题 `53357761` 已完成导航并广播一次，但合同把广播/协调语义标为 unsupported。第二、三条广播依赖这个不能满足的条件，被执行器拒绝；外部要求至少三条，最终失败。B1 同题通过。

应区分“执行是否安全且合法”“是否推进了任务”“是否有充分证据宣告全部完成”。当前三者共用条件状态，unknown 一旦被列为动作前置，执行器便不区分原因地阻断下游。对目标、悬停、照片等语义的保守解释又容易沿依赖链传播，让后面的可执行动作都无法发生。

### 4.5 Memory 和恢复没有解决根因，反而增加约束

新版确实记录了观测来源与时效，但错名合同不会因新观测而被修订。因此“反复读状态”无法解决这批主要缺口。另一方面，运动会令位置证据失效；系统将受影响条件当成可能被破坏的受保护目标，要求恢复声明。通信题中水平移动仍保持 z=19，模型却先被“扰动已满足高度”规则拒绝。

**旧证据需要重读，不等于实际高度需要恢复。** Memory 应帮助执行器获得足够相关的事实，不应把每次缓存失效都变成额外行动义务。当前证据没有支持“跨任务 Memory 污染是主因”的判断。

完整 11 题、五条因果链、execution_id 与原始 trace 的映射见 [CASEBOOK_CN.md](CASEBOOK_CN.md)。其中源码锚点全部对应 [运行归档 source.zip](../../../experiments/runs/20261006-115922-harness-pilot-3f71f966/source.zip)，不是回退后工作区的代码行。

## 5. 不是只有自判收紧，也不主要是时间或服务问题

正式 Harness 11 题全部外判失败、自判失败：10 次 incomplete、1 次 contract_rejected，**没有外部通过但自判未完成**。它们中 4 题零 mutation，6 题只有起飞或重复调高度，只有通信题推进了水平导航与一次广播。60 条计划记录有 55 条带 error；部分是在合法前缀执行后报错，不能将其写成 55 次完全零执行。

B1 所有 18 个已计分题中，自判成功 17 个，虚假完成 5 个，真实超时 1 个。这说明 B1 的完成判定仍有问题，但减少虚假完成不能以阻断正确任务执行为代价。新版同时失去了本可得到的 8 个成功，并未产生任何新增成功。

共同 11 题的可观测资源如下：

| 指标 | B1 | Harness |
|---|---:|---:|
| 有 usage 的模型调用数 | 213 | 96 |
| 总 tokens | 21,496,501 | 13,563,614 |
| 从任务窗口打开至冻结可判题的中位耗时 | 110.21 秒 | 255.66 秒 |

这里的窗口耗时包含截止后的排空与冻结；案例簿另列 job 时长，两种定义不能混用。

不能声称新版总 tokens 更多。它的调用少、tokens 少，但任务推进更少、耗时更长。单个简单旋转题两边同为 7 次调用，新版约 97 万 tokens，B1 约 8.6 万；全量逐字段 Memory、合同重复传入、编译与审查增加了单次请求负担。没有消融实验，不能量化这一负担的独立影响。

已计分题没有记录到 provider HTTP 失败；正式 Harness 11 题均未超时。B1 的 `529c0622` 在用户停止前已发生真实 500 秒超时，保留为失败；正在运行的 B1 `23a9d67d`、Harness `018d1d05` 标记为用户中断。当前首要修复对象是确定性的接口和执行语义，而非加预算或换模型。

## 6. 为什么之前的检查没有拦住

已有 Harness 单元测试大量使用预写的正确 JSON 和 FakeModel，验证“规则按设计拒绝了某动作”“给定正确合同可以推进”。这不等价于真实模型产生的合同可解释，也不等价于那些规则有利于任务成功。

这里有两层责任：实现层缺少共享的谓词/参数/命令类型约束；设计层没有先证明“新增门控不会阻断合法任务推进”，就让它控制全部执行。此前对单元测试通过所代表的就绪程度估计过高，冒烟已显示的阻塞也应更早触发停机分析。应由架构与接口承担这次失败的解释，不能归咎于模型“不够遵守格式”。

## 7. 后续最小路线：从 B1 出发，逐层证明收益

以下是建议，本轮没有实施新的 Harness 修改或发起新模型实验。

1. **B1 保持执行主线。** 先加旁路日志、工具回执整理和任务进度提示；保留已投入的来源、时效、ID 校验和任务隔离资产，让它们帮助动作选择。
2. **先打通统一能力定义。** 从同一份注册表生成模型 schema、提示、谓词 evaluator 和真实工具/事件名；把当前原始模型产物作为离线接口回放样本。修正拼写接线只代表阻塞被修复，不代表任务成功率已恢复。
3. **拆开三个层次。** 物理/安全调用前提使用可靠事实；任务顺序表达“先后”；完成证据决定能否宣告成功。不能将 unsupported 伪造为 satisfied，也不能删除真实安全前提来掩盖问题。
4. **修复只用于真实执行失败。** 正常多机行动允许推进独立分支；证据失效先观测，实际状态破坏才恢复。错误任务解释应有受审计的局部修订出口。
5. **未来再做最小消融。** B1 → B1+旁路 Memory/进度 → 加可解释合同但不否决行动 → 只加已验证的具体前提。每次只改变一个层次，再决定是否值得增加强制门控。优先指标始终是原外部任务通过，其后才是虚假完成、恢复收益、时延与 tokens。

本次是早停、单场景前缀、没有新增成功的负面实验，不支持论文中“全新架构提升成功率”的主张。它能支持的研究判断是：未经对齐的形式化合同与执行门控会产生系统性过度约束；后续架构必须明确如何避免这种失效，并以独立任务、清晰消融验证收益。

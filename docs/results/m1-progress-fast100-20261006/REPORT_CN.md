# M1 fast100 对照验收报告

2026-10-06，北京时间。结论：**本轮完整、可核验，但当前 M1 不通过性能增益验收，暂不建议将冻结版本直接扩大到 dev240。** M0 成功 80/100，M1 成功 78/100；同 100 题改善 2 题、退步 4 题，净减 2 题。M1 的证据账本正常启用，尚未转化为任务成功率收益。

## 1. 实验边界与完整性

| 项目 | 本轮执行 |

| M0 | B1 targeted remedies，`cb80fde8269a09795782a6ef046d04c381b3f3c9` |
| M1 | M0 加任务局部证据账本与有界动态摘要，`3161fc88c7d4c9646e2190eaa22816fedc02f380`，标签 `m1-progress-state-v1` |
| 模型 | 官方 DeepSeek，实际遥测模型名 `deepseek-flash`，temperature 0.1 |
| 数据 | fast100 开发集，原 5 场、100 题、605 检查，任务原顺序 |
| 执行 | 每臂 2 个场景 worker，每题 500 秒；先 M0 后 M1 |
| 状态 | 两臂均 `completed_and_verified`；持久任务 completed，两阶段 exit code 均为 0 |
| 补跑 | 0；每场 generation=1，无恢复、重启或失败题重试 |
| 评分 | 沿用冻结外部 checker；超时后关闭动作、收尾、冻结环境再评分 |

两臂均完整计分 100/100 题和 605/605 检查，无未计分题。完成后再次调用各自归档的 `m1_progress_pilot.py verify`，封存文件、方法身份、数据、依赖/公共运行时及保存世界状态的检查重放均通过。详见 [verification.json](verification.json)。复核不执行模型调用，不产生新 attempt。

原 B1 的 50/57 中断试验保持原样。本轮 M0 是同 fast100 的新对照，不能与原 B1 的不同分母混合。

| 指标 | M0 | M1 | 相对变化 |
|---|---:|---:|---:|

| 100 题评分就绪时间之和 | 13,811.67 秒 | 14,588.51 秒 | +5.62% |
| 每题平均评分就绪时间 | 138.12 秒 | 145.89 秒 | +5.62% |
| LLM 调用数 | 1,518 | 1,493 | −1.65% |
| 输入 token | 112,679,106 | 120,795,739 | +7.20% |
| 输出 token | 2,866,990 | 2,891,076 | +0.84% |
| 总 token | 115,546,096 | 123,686,815 | +7.05% |
| 输入缓存命中 token | 106,481,016 | 7,317,120 | — |
| 输入缓存未命中 token | 6,198,090 | 113,478,619 | 18.31 倍 |
| 输入缓存命中率 | 94.50% | 6.06% | −88.44 个百分点 |

墙钟时间来自 `performance.json` 的 invocation；M0 为 15:26:35–17:56:19，M1 为 17:56:21–20:26:40。持久任务在 20:26:47 完成收尾。评分就绪时间为每题 `barrier.frozen_at − window.opened_at`，包含执行、轮询与冻结等待，不包含全部场景准备。两个 worker 并行，因此逐题时间之和不能当整臂墙钟时间。

Token 采用保存的 provider usage（包括超时任务的已完成调用），100 题逐题总和与汇总遥测逐字段一致；没有把 HTTP usage 和 LLM callback 重复相加。两臂均无 LLM 失败回调、HTTP 错误或未完成调用。M1 有一次资源采样 `TimeoutExpired`，影响资源采样完整性，不是模型请求失败或任务退出；本报告不以 CPU/RSS 下降主张收益。

**缓存下降是继续扩大前必须排查的问题。** 冻结源码把随步骤变化的摘要附加到每次请求的 system message。这与本轮缓存命中大幅下降相符，但当前没有逐次模型请求正文，也没有控制服务端缓存状态的对照，故只是待验证解释，不能认定缓存机制的因果效果。本报告未估算货币成本。

## 4. 六个胜负变化案例

| 配对 | 场景 / 任务 | 外部检查 M0 → M1 | 保存证据支持的诊断 |
|---|---|---:|---|
| W | ad34350a / 529c0622，多目标巡检 | 0/4 → 4/4 | M0 超时；M1 指定 Drone 13 新增两个目标的到达记录，并通过两个拍照检查。两臂进入本题时历史不同，不能将其直接归因于摘要。 |
| W | ad34350a / a53ba7fc，四机编队 | 7/16 → 16/16 | M0 最终回答缺少 `[TASK DONE]`，保存动作链停在编队导航阶段；M1 完成后续定向移动，外部检查全通过。 |
| L | 3973d0d6 / fb2c7ba3，多目标到达 | 2/2 → 1/2 | M1 超时，Fixed Target 3 在最终账本仍 unresolved，指定 Drone 4 没有到达该目标；另一个目标通过。 |
| L | 823c15d5 / c6e28e3b，顺序多目标访问 | 3/3 → 0/3 | 两臂均超时。M1 三个目标均 unresolved；M0 的检查存在明显历史承接，见下文。 |
| L | 823c15d5 / 5aa74653，三机目标扫掠 | 12/12 → 9/12 | M1 完成 9 个定向移动检查，但三个指定无人机到达目标检查均失败；Fixed Target 4 未解析，另外两个目标已解析但指定无人机未完成到达。 |
| L | 35ce64d8 / 20742d37，五机目标扫掠 | 20/20 → 4/20 | M1 超时；Fixed Target 10、11 未解析，两个指定到达检查和大量后续定向移动检查未通过。 |

`c6e28e3b` 的外部检查只有三个 `target_is_reached`，没有验证原文中的指定执行无人机、顺序、悬停和照片。在 M0 的该题开始前，Fixed Target 55 和 31 已是 reached；结束时三个目标都 reached，但记录中的执行者并非原文指定的 Drone 10。因此，这个 L 保留在冻结基准成绩中，**不能被描述为“M0 完整执行了顺序拍照任务而 M1 没有”**。两臂场景历史差异是真实协议的一部分，不能事后删掉该题或换用更严格评分以改变主结果。

`5aa74653` 中 M1 最终文本称目标不可发现或路径不可达；这只是 agent 的声明，不能作为环境事实。保存的世界状态含有该目标，而更强的全局不可达结论没有证据。账本仍正确地保留 unresolved 或动作 blocked，不能由这些标签推导任务已完成或客观不可能。

异常文本中出现的 “cancelled by user” 需结合 timeout 记录解释：这里是冻结 runner 在达到时间窗后取消执行的通用错误文本；本轮持久任务没有收到用户终止信号，两臂完整结束。

六例的命令、回执引用、失败检查和到达状态前后值保存在 [changed-cases.json](changed-cases.json)。这些诊断说明失分位置，不构成因果归因。

## 5. M1 是否实际生效、证据绑定是否正确

| 核对项 | 结果 |
|---|---:|
| M1 保存 toolchain / ledger | 100 / 100 |
| `task_progress_mode=summary` 且 `task_progress_active=true` | 100 / 100 |
| `observer_errors` | 0 |
| 账本工具事件 | 3,390 |
| 未结束账本事件 | 0 |
| 可与原 tool_chain 交叉核对的完整回执 | 2,527 / 2,527 一致 |
| 命令身份、原文片段、实体匹配、证据 ID、失效引用及条款链接结构问题 | 0 |
| 显式实体名引用 | 235 exact、20 unresolved（按任务分别计数） |
| 原文条款 | 215，其中 94 无显式实体名 |
| 事件有实体关联的原文条款链接 | 1,817 / 3,390 |
| `mission_completion=not_evaluated` | 100 / 100 |

七道超时任务的原 `tool_chain` 为空，但各自 ledger 保存了合计 863 个事件。这些事件可用于诊断；不能宣称已与不存在的原 tool_chain 回执逐条交叉核对。其余 93 题按工具名、归一化参数、完整返回 payload 的多重集比对，2,527 条均一致，并行完成顺序不作为错误。

M0 的旧实现没有 task_progress 字段。其关闭状态由冻结的 `UAV_TASK_PROGRESS_MODE=off`、方法源码和执行环境核验支持，不能因旧 trace 缺少字段而判为配置失败。

结构链接只回答“这个工具涉及了原文中哪些实体”，没有表示“这项义务已完成”。例如，单次 `list_drones` 可关联多个条款；多机任务的 “all three drones”“then” 也不会自动得到执行主体和先后关系。94 个无显式实体名的条款不是 94 个失败任务，20 个 unresolved 也不是新增性能指标。更严格的历史/陈旧/未知标签，不等于成功率收益。

冻结实现对摘要有 4,000 字符上限，但本轮未保存每次注入的模型请求正文。此处确认的是已配置且正常运行的 middleware 和最终账本，不能声称已逐次审计实际摘要内容、模型注意力或模型采纳行为。

## 6. 阶段判断与下一步建议

**本轮可收束为一次有效的负向开发实验。** 实现/实验完整性验收通过；成功率增益验收未通过；成本未改善。保留 M0 为当前已接受基线，保留 M1 方法和全部证据，不把 M1 宣称为已验证提升，也不自动进入 dev240、M2 或 M3。

对六页论文，更合适的主张候选是：在局部可观测的多机协作中，将“发现某目标”转成“指定执行者完成该目标义务”的可追踪交接。当前证据只支持把它列为下一步可检验假设，尚不足以宣布机制成立。单纯增加一份通用证据摘要不能作为当前论文的主要正向贡献。

建议按以下顺序继续，付费实验须等用户决定：

1. **先做离线诊断。** 沿六个变化案例与同类失败定位目标何时被发现、是否分派给指定无人机、是否真正执行、后续义务是否被跳过；区分搜索、导航、主体分派与停止问题。避免同时加入去重、重试、超时和全任务 verifier。
2. **如继续 M1，先提出一个最小修订并单独命名。** 优先检查任务相关实体/待办关系是否在摘要预算内被有效保留，同时把动态摘要的注入位置与缓存成本分开验证。保留 M0、冻结 M1 和新增机制的开关，形成可复现的累计消融。更改摘要方式不是本轮 M1 的结果，不能悄悄覆盖本版或把它算作 M2 的成功。
3. **只有新的 fast100 证据支持，才申请 dev240。** 主判断仍为原任务成功数、完整 W/L、场景分布及时间/token；成本/缓存用作约束。需看到能够解释的成功改进及可接受代价，而不是仅内部标签更严格。若引入“发现→指定执行”机制，先证明适用失败足够集中，再在保留状态层的基础上做增量比较。

fast100 只有 5 场，且是利用历史信息构造的开发集。题目在场景内共享世界和黑板，两臂固定 M0 先、M1 后，每臂仅一次。故本报告不宣称随机因果实验、统计显著、独立同分布的 100 次重复、全量提升或未见数据泛化；也不从 −2 题推出 M1 在所有设置都无效。

## 7. 交付物与复核方式

- [paired-tasks.csv](paired-tasks.csv)：原场景/任务顺序的完整 100 行、35 列，含两臂成绩、超时、时间/token、W/L 和原始 trace 路径。
- [summary.json](summary.json)：整臂、逐场和配对汇总。
- [evidence-audit.json](evidence-audit.json)：逐题 ledger 与回执核对。
- [changed-cases.json](changed-cases.json)：六个胜负变化案例及历史状态证据。
- [verification.json](verification.json)：冻结 verify 入口、退出码、原输出和核验时间。
- [input-sha256.json](input-sha256.json)：本报告读取的输入文件 SHA-256，包含两臂 suite seal。完整归档的其余文件由 seal 及冻结 verify 传递核验。
- [artifact-sha256.json](artifact-sha256.json)：本目录交付文件的 SHA-256（不包含其自身）。

CSV 中 `scoring_ready_seconds` 的单位是秒，token 字段为 provider 观测整数；布尔值用 true/false，标识符保留文本。`recorded_tool_steps=0` 在超时例中表示该记录未保存步骤，不是没有调用工具。机器读取时按文本读取 scene/task ID。分析脚本仅从归档读证据，在本目录写派生材料，不改运行、方法、数据和评分。

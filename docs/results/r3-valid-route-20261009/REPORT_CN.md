# 可执行航线集上的 R2/R3 首次配对结果

日期：2026-10-09。研究对象：R3 的“按无人机和原始顺序追踪剩余航点”证据反馈。**结论：机制工作正常，但这两道新题没有带来分数收益。** 两题均由 R2 独立完成，故不存在可供 R3 救回的对照失败。

## 预注册与可比性

任务集在任何模型结果出现前，按固定种子和离线合法性规则选出前两个候选；原服务端试飞分别通过 26/26 检查。规则、生成和试飞见 [前期审计](../../audit/r3-valid-route-prospective-20261009/REPORT_CN.md)。在线试验从同一冻结场景 JSON 分别启动新服务和空 blackboard，四次首次可评分尝试按预定顺序 `第一题 R2→R3，第二题 R3→R2` 完成。R2 与 R3 的封存 Python 源文件差异仅为 `uav_agent.py`、`task_evidence_r3.py` 及其离线测试；同模型配置、依赖、500 秒窗口、原服务端检查器和评测器。

四次尝试均由评测器标记为 `completed_and_verified`，没有模型重试、超时或缺失检查。启动时各对的无人机位置、电量、状态一致；服务端动态天气会在准备阶段轻微漂移，因此不能声称任务前环境逐字段完全相同。模型采样本身也不能锁定成相同动作。

整题 R3 胜 0、负 0、平 2；叶检查差 0。时长一题快、一题慢，token 总量只差 600；两题且运行次序相反，不能推出稳定的速度或成本改善。

## 机制到底发生了什么

- R3 两题均返回 `recognized_coordinate_routes`，正确绑定 `Drone 1`、`Drone 2` 的 ID。最终每条路线的 `ordered_prefix` 都是 **12/12**；证据指向对应无人机的真实 `navigate_to` 成功回执或 `move_along_path` 成功点。没有观察器错误。
- R3 分别产生 3、4 次含路线视图的请求前消息注入；模型请求审计分别记录 7、7 次 wire 请求且无审计错误。这证明路线反馈机制被运行并进入请求构造过程；不能把它直接等同于模型因反馈而改变了决策。
- 四个臂的实际导航工具输入均按任务文本的原顺序覆盖两架无人机各 12 点，然后落地。第一题 R2 先用两次 `navigate_to_and_sense` 到起点，再各用一次批量路径工具走剩余 11 点；R3 各用一次批量路径工具走全 12 点。第二题两臂都先导航到起点，再批量走剩余 11 点。
- 两题没有失败的移动回执、漏航点或需要恢复的分叉。R3 最终路线证据完整，但它追踪的缺口并未形成能区分 R2/R3 的实际任务需求。原检查器在本轮只计访问、终点和落地；实际工具输入额外确认了四个臂都按文本顺序飞行。

## 对研究主线的判断

这一步解决了原场景“指定点本身不可达”造成的机制检验混淆；但新的可行航线被 R2 很快用批量路径工具完成。**不能把 R3 在此实验的路线跟踪正确性写成任务成功率提升**，也不能把第一题的较短时长单独挑出来作为加速证据。原 1,500 题及既有 R3 prefix 分数保持独立；本轮 2 题是新的机制探索集，不代表原 benchmark 的难度分布。

下一步宜停止扩大同样格式的 R3-only 路线试验，先从原始失败中寻找**可执行且确实存在遗漏/恢复机会**的任务；若找不到足够样本，则把 R3 定位为可靠的证据记账组件，论文主增益应转向已有失败证据更支持的机制，例如超时关键路径或验证误判。任何新的挑战集都应在查看模型结果前冻结合法性、场景和配对规则。

# 最小 harness 同技能在线实验：最终验收与研究判断

验收日期：2026-10-16。五臂均已完成并通过封存复核，共 500 次任务执行、3,025 个评分检查点。本次只汇总、核验和分析已有证据，没有补跑、调用模型或修改冻结实现。

**本轮支持继续研究“在执行条件仍成立时继续技能，只在需要新决策时交回模型”。** applicability 相对 every_step 从 76/100 提升到 85/100，500 秒窗口内模型调用从 2,405 降为 1,400（−41.8%），配对结果为 10 胜 1 负。平均评分就绪时间下降 6.9%。但目前不能声称 applicability 是最佳门控：failure 为 84/100，调用更少、平均时间更短。单次开发集、固定运行顺序和任务间状态继承，都限制了因果与泛化结论。

## 1. 验收范围和指标口径

冻结顺序为 fixed4 → R2 → applicability → every_step → failure；每臂 100 题、605 检查点、每题 500 秒、两个场景 worker。全部保留首轮结果。队列从 2026-10-15 15:40:32 运行到 2026-10-16 03:19:39，历时 11 小时 39 分 7 秒（北京时间）。

逐臂重新执行各自封存运行时中的 `coordinated_search_pilot.verify`，核对套件文件清单及哈希、源码归档、五个场景首轮封存、评分完整性。五臂均为 `valid_complete_run=true`，每臂 100/100 题和 605/605 检查点完整，缺失或无效任务为 0。500 条任务轨迹可定位，遥测无损坏行。所有 8,185 次模型 HTTP 尝试均有 200 响应，逻辑请求均有结束事件；未发现模型服务错误、HTTP 重试或额外窗口外模型调用。任务超时和代理循环耗尽仍作为任务结果保留，不能因为服务正常就排除。

指标定义：

- **任务成功**使用冻结 checker 的完整任务判定，不使用模型自述，也不使用 trace 的 `success` 字段替代。
- **逻辑调用**按准入窗口内请求计数；本轮与全轨迹计数一致。**HTTP 尝试**单独从遥测计数，本轮恰与逻辑调用相同。
- **评分就绪时间**为任务窗口开启到评分屏障冻结的墙钟，包含收尾、轮询等待。它不等于模型推理时间，也不是五臂队列总历时。
- **模型处理墙钟**为请求处理器从开始到结束的计时，包含网络和服务处理；不能解释成模型内部“思考时间”。
- 后文时间均覆盖完整 100 题（包括失败题）。失败较早退出也会让平均时间缩短，必须连同成功率阅读。

## 5. 模型是否正确选择和恢复技能

四个 harness 臂共有 52 次适用题机会，实际提交 51 个计划：fixed4、applicability、every_step 各 13 个，failure 为 12 个。所有提交的技能类型均匹配冻结语法，没有在不支持的任务上提交执行计划。failure 的 `85e6de6f` 没有调用技能，转用原始起飞、悬停工具完成；这是一次选择漏用，不是技能执行失败。

模型的启动选择并不完美：共 69 次 start 尝试，含 14 次对不支持任务的尝试、3 次多传控制字段、1 次重复启动已提交技能。14 次不支持任务尝试被计划编译拒绝。fixed4 的 3 次字段错误随后更正成功。failure 的重复启动发生在 `needs_replan` 之后，被 `skill_already_committed_use_plan_id` 拒绝。自动汇总中的 `control_rejections=0` 不覆盖包装层拒绝，因此本报告补读了 `tool_chain` 观察记录；不能据该计数宣称零控制错误。

对全部 27 个简单链计划，逐一核对原始命令、提交的动作顺序与数值、公开无人机名称到 ID 的绑定、实际动作调用和最终评分。未发现错机、漏步或重复执行已完成简单链步骤；这些任务均通过。这个结果只覆盖当前狭窄的完整匹配语法，不能外推为任意自然语言任务的正确编译能力。

恢复证据如下：

| 实验臂 | resume 调用 | 从 paused 进入执行且 plan_id / cursor 连续 | 对终止状态的无效恢复 |
|---|---:|---:|---:|
| fixed4 | 61 | 61 | 0 |
| applicability | 0 | 0 | 0 |
| every_step | 898 | 898 | 0 |
| failure | 17 | 16 | 1 |
| 合计 | 976 | 975 | 1 |

975 次有效恢复均沿原 `plan_id` 和暂停 cursor 继续，未发现换计划或从头重置。failure 的第 17 次 resume 指向已进入 `needs_replan` 的旧计划，接口返回原状态，没有再次进入技能。这证明接口阻止了错误续跑，也证明模型仍可能误判何时该恢复。applicability 没有调度暂停，不提供在线 resume 验证样本。全部恢复均为进程内恢复，没有验证崩溃重启后的持久恢复。

## 6. needs_replan 后的真实接手结果

审计全部 6 次真正的 `needs_replan` 退出，区分调度暂停和计划失效。表中“后续动作”指模型通过原始工具发起的动作数量，不代表有效动作数量。结束进度来自封存快照；四个通过案例另有模型可见的进度观察与动作回执支持。

| 臂 / 任务 | 退出原因 | 技能末次进度 → 结束进度 | 后续模型调用 / 动作 | 任务结果 |
|---|---|---:|---:|---|
| fixed4 / 5e743d21 | 局部修复预算耗尽 | 67 → 94 | 18 / 154 | 未通过，超时 |
| applicability / 5e743d21 | 局部修复预算耗尽 | 81 → 96 | 28 / 108 | 通过 |
| applicability / b1ad4f3e | 无公开候选 | 95 → 100 | 5 / 1 | 通过 |
| every_step / 9c0b52a0 | 搜索轮数上限 | 66 → 66 | 24 / 62 | 未通过，超时 |
| every_step / 7eba7390 | 搜索轮数上限 | 66 → 100 | 6 / 6 | 通过 |
| failure / 5e743d21 | 局部修复预算耗尽 | 88 → 97 | 23 / 136 | 通过 |

最清晰的有效接手是 applicability 的 `b1ad4f3e`。技能在 95% 时因无候选退出，模型重新读取进度并检查公开目标信息，在 tool_chain 第 18 项发现 `Fixed Target 17` 尚未到达。第 24 项让 Drone 6（`d32ef0d8`）导航到 `(680,655,20)`，回执 `arrival_verified=true` 且明确记录到达该目标；第 25 项公开进度升为 100%，最终 checker 通过。这条证据链支持“识别剩余目标并完成接手”，不只是“后面还有动作”。

every_step 的 `7eba7390` 在技能搜索停于 66% 后改用多机长路径覆盖。第 98 项路径回执记录到达 `Fixed Target 3`，第 99 项公开进度为 100%，checker 通过。其中另一路径只部分完成，不能把所有接手动作都算作正确动作。

applicability 和 failure 的 `5e743d21`，公开进度分别连续上升到 96% 和 97%，末段导航回执包含实际到达目标，最终 checker 通过，支持目标层面的有效接手。但二者 trace 最终均标为 `step_limit`，failure 还夹杂重复 start 和对终止计划的 resume。因此准确表述是“接手后达到了评分目标”，不能写成“所有恢复决策正确且代理正常收束”。

两条失败轨迹同样重要。fixed4 接手时仍有约 435 秒，后续 154 次动作最终只到 94%；every_step 的 `9c0b52a0` 接手时仍有约 406 秒，62 次后续动作后仍是 66%。它们的异常轨迹没有完整 tool_chain 观察列表，审计使用剩余事件、API 回执及评分快照，保留这一证据缺口。两例不能认定修复成功。4/6 只是本轮不同臂、不同初态下的描述性个案计数，不是可泛化的“恢复成功率”。

## 7. 每步交回的另一项代价：循环预算耗尽

every_step 的 `5e743d21`、`24ac1838`、`7cdefb56` 均有原始错误 `Recursion limit of 450 reached without hitting a stop condition`。三题各调用模型 225 次，分别在约 275.8、286.0、300.9 秒评分就绪，未用完 500 秒；计划 cursor 为 224、224、223，最终标记 `abandoned / task_ended_with_unfinished_plan`，进度为 81%、92%、93%，全部未通过。

这三例表明：频繁交回模型会消耗外层代理循环预算，即使 plan_id 恢复完全正确，也可能在技能完成前终止。这是本冻结运行时中的真实调度成本；同时也是实验限制——结果不能只解释为推理延迟节约。下一轮需要将执行期限与外层循环预算分别控制，检验收益是否仍然存在。

## 8. 当前可用的论文主张与下一轮验证

目前可以提出并诚实支撑的主张是：**我们实现了一个基于显式计划与执行证据的可中断 harness，将简单动作链和现有搜索技能统一为可继续、可暂停、可按计划恢复、可交回模型的执行接口。在本次冻结开发集同技能对照中，减少调度性回交降低了模型调用，并缓解外层循环预算耗尽；任务效果需要结合技能适用范围、状态继承及实际接手证据评估。**

这条论文路线仍成立。故事应围绕“模型何时需要重新决策、执行器何时已有足够依据继续”，将贡献落在计划契约、失效与调度暂停的区别、恢复边界及可审计验证方法上。本轮没有直接测量或控制模型内部思考过程，也没有证明相对所有既有 harness 的架构新颖性；不能把每次少调用都称为减少了不必要思考。

接下来最有价值的验证按优先级为：

1. **消除初态与顺序混杂。** 预先冻结独立验证集；在可行时从相同任务快照开始，并另保留真实顺序继承协议。多次重复，平衡实验臂运行顺序。主结果仍报告完整任务成功，适用集合继续预先声明。
2. **分离调度收益与循环上限。** 将当前 450 步外层上限作为明确实验因素，另设足以完成同一技能轨迹的预算；同时统计任务期限、调用数、HTTP 尝试、模型处理墙钟，避免只靠 every_step 提前耗尽来获得优势。
3. **针对“必须重新决策”的事件验证门控。** 固定条件变化、动作效果不明、外部动作使旧绑定失效、局部修复无进展等情形；标注应继续、应暂停、应重规划，测量错放行、过早交回、错过交回和检测延迟。failure 与 applicability 共享强制守卫，现有对照不足以证明更强的适用性判断。
4. **改进接手契约并做独立验证。** `needs_replan` 返回已完成义务、剩余目标、失败证据、不能重试的动作与剩余预算；验证模型是否按此改变方案，而非重复 start/resume。把目标达成与代理正常结束分开计分，补足异常退出时观察日志的覆盖。
5. **扩展而非掩盖技能覆盖。** 当前只有 13/100 题适用，且搜索中存在大量继承完成状态。下一版本先解决搜索候选耗尽与低进展，再逐步扩大可编译任务；新增覆盖必须单独报告，不能混入调度消融。

这些是下一版待冻结的方案，本次验收没有启动任何新增实验。当前证据不足以宣称显著性、非劣性、跨模型泛化、最优门控、所有失效均被正确识别或持久恢复可靠。

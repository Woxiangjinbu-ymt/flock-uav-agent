# Memory 第二版：优化与小规模验证

日期：2026-10-16。

**这一轮完成了提示压缩和重复检查建议，但“记录里查过，模型仍重复查询”的问题还没有解决。** 同样的 6 个场景、两组共 12 次真实模型执行已经跑完，没有扩大到 100 题。路线场景的输入量下降了，但整体收益很小，还出现了已完成任务多查一次状态的负例。

## 这次具体改了什么

第一版只是把查询历史列出来。第二版把同一位置的成功空查询合并成一条：**谁在什么位置查过、查过几次、对应哪个目标、证据来自哪里**。符合条件时，明确建议“当前位置已查过，条件没变就换个可行的观察位置”。

这个建议只用于当前执行者的静态目标定位。查询失败、移动、感知条件变化、动态目标或用途不同，都允许重新查询；系统没有拦截工具，也没有用缓存冒充新的工具结果。

同时去掉重复任务原文、空字段和整串历史动作，路线只突出已完成前缀、下一个航点和剩余任务。完整原始记录仍保留。新模式为 `evidence_memory_v2`、`evidence_memory_v2_harness`，默认不开启，第一版继续保留。

## 怎么验证

逐字节复用第一轮的 6 个场景快照和真实历史回执，重新跑 **R3 基线 vs memory v2**。两组使用相同模型、工具、原始信息和读取时点，每例各跑一次；没有挑选重跑结果。模型为 `deepseek-flash`，温度 0.1，关闭 thinking 和 SDK 重试。

本轮还修正了双方共用的预算预检：按实际发送内容计算预留量，不再计入 SDK 内部元数据。每次仍最多 6 次模型调用、12 次工具调用、90 秒、60,000 token。本轮没有预算截断；旧版实验的数字仅作历史背景，不拿来替代本轮基线。

## 结果

| 指标 | 本轮 R3 基线 | Memory v2 |
|---|---:|---:|
| 任务目标达成／正常结束 | 6/6 ／ 6/6 | 6/6 ／ 6/6 |
| 同机同位置重复感知 | 2 | 2 |
| 模型调用 | 22 | 23 |
| 工具调用 | 18 | 19 |
| 总 token | 66,583 | 66,351（−0.35%） |
| 执行耗时合计 | 25.01 秒 | 26.12 秒 |

| 场景 | R3 → v2 token | 实际变化 |
|---|---:|---|
| 水平历史线索 | 19,876 → 19,465 | 仍在已查位置重复感知；动作相同 |
| 垂直历史线索 | 19,784 → 19,668 | 仍重复感知；仅最初两次读取顺序不同 |
| 路线中断 | 9,124 → 8,354 | 动作相同，token 减少 8.44% |
| 路线受阻后恢复 | 9,644 → 8,859 | 动作相同，token 减少 8.14% |
| 已完成任务 | 2,060 → 4,181 | 基线直接结束，新组多查一次状态 |
| 感知失败 | 6,095 → 5,824 | 两组都正确重试，再访问目标 |

重复感知指标只用于这个固定模拟时钟下的同机同位置诊断，不能泛化为所有重复查询都无用。耗时包含模型服务波动，不作显著性结论。


## 哪些有进展，哪些没有

**压缩有局部效果。** 路线场景两组都是“补剩余航点→终点→降落”，模型和工具调用数完全相同；较短表示让这两例 token 各减少约 8%。首次路线视图由本轮 R3 的 895 字符压到 525 字符。但路线续接本身没有超过 R3，成功率也没有增加。

**重复查询仍是主要问题。** 两个线索场景中，真实请求都包含“当前位置已有两次空查询”和换位置建议。模型还在回复中承认之前查过，却依然先刷新一次；垂直场景第二次决策明确提到了换位置建议。这说明问题已经从“记录是否送达”，转为“模型是否据此改变行动”。

**结束判断仍会多做确认。** 已完成场景中，新组知道历史动作已完成，却又读取状态确认降落。视图中的“降落等条款未核验”可能促成额外确认，但单例不能证明原因。不能简单删除这类边界说明来换取省调用，下一步应考虑如何引用已有的成功降落回执。

本轮评估的是“紧凑记忆＋条件建议”的组合；没有分别验证两部分的独立贡献。六例都已用于开发，不是独立测试集，不能据此宣称普遍提升。

## 下一步建议

先验证一个更明确的决策步骤：模型在同一次行动输出中选择“沿用已有结果／换位置／刷新”，若刷新，指出需要更新的事实及对应的新证据，例如位置变化或上次失败；将仅为“再确认一下”的调用单独记录。先不拦截工具，检验这一步是否改变选择。

若之后加入执行层拒绝重复查询，应单独做对照，区分 memory 提供证据的作用与执行规则的作用。本轮停在这里，保留全部负结果，没有追加试验。

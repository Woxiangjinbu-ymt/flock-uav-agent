## 模型行为与失败恢复

**短链：有一个明确的局部效率案例。** I 在第 3 次模型响应自主选择 `run_harness start/simple_chain`，子程序完成起飞和悬停；B 用原工具完成相同两动作。I 减少两次模型请求、节省 16,013 token，但公开环境 API 从 9 增至 13。因此它节省的是本例模型交互成本，不是所有执行成本。

**导航：相同原工具路径，整合上下文增加成本。** 两臂均为 list/weather → sense → takeoff → navigate → hover → final，均无参数错误，均 6 次模型请求、13 次公开 API 和 3 个动作。I 增加 8,446 token；这一结果与额外工具/状态/提示的成本一致，但本批没有拆分这些输入成分，不能精确归因于某一个模块。

**搜索：更多动作与部分进度，没有整题成功。** I 在第 3 次响应自主选择 `public_search`，该一次模型决策内部执行 345 次 API、85 个动作，达到 16 轮后以 `needs_replan / round_limit_below_threshold` 退出。当时公开进度 66%；模型随后改用原工具继续，没有 resume/restart，最终仍未完成。评分侧最终进度 B 为 33%（1/3），I 为 66%（2/3），两者均未严格超过 95%。B 的 33% 来自评分侧最终状态，不伪称模型曾显式读到该进度。

I 最终共 488 次公开 API、110 个动作，其中 85 个动作属于子程序，25 个来自模型原工具。B 为 77 次 API、19 个动作。I 还出现两次把 `input_json` 传成对象的工具校验错误，模型之后改成字符串继续。I 的 239,897 token 中，202,610 来自子程序退出后的 7 个模型响应及其输入，说明成本主要花在后续原工具搜索交互；不能把全部成本归给那次子程序提交或单一状态模块。分段与评分侧进度来源见[补充核验](analysis-01/review-notes.json)。搜索 I 的额外 token、动作和时间没有换来整题成功；66% 不能单独称效率改善，也不能把内部 85 个动作写成 85 次模型决策。

**受控回执丢失：真实后续决策成立，但两臂都能恢复。** 两臂都在指定 UAV 第一次真正起飞至 12m 后丢失回执，且此前未完成 hover。随后链条如下：

| 证据环节 | B | I |
| --- | --- | --- |
| 第 3 次模型决策 | 原工具 `take_off` | 自主 `start/simple_chain`，内部起飞 |
| 模型可见反馈 | 中性超时错误 | 子程序内部公开查询状态后退出；返回 unknown、当前位置与禁止重放建议 |
| 第 4 次实际模型请求/新决策 | 收到超时后，自主 `get_drone_status` | 收到退出及恢复视图后，自主 `get_drone_status` |
| 第 5 次新决策 | 原工具 `hover` | 原工具 `hover` |
| 实际效果与重放 | 起飞一次、悬停一次；重放尝试 0 | 起飞一次、悬停一次；重放尝试 0 |

原始 call ID、请求、工具回执和世界动作关联见[独立分析](analysis-01/analysis.json)中的 `unknown_recovery`。这里确有每臂 **1 次“已见故障且仍有悬停义务”的后续决策机会，均完成恢复**；不是同一回复预选的并行动作。I 子程序内部的状态查询另计为程序动作，不当作模型恢复；I 最终 ledger 仍保留起飞效果 unknown，没有根据后续状态回写历史动作成功。

这补上了新版契约的真实模型恢复案例，但 B 同样查询状态并完成任务，I 反而增加 16.5% token。真实 ready/paused 可恢复子程序机会仍为 **0**，resume 次数为 **0**，resume 恢复率不可估计。此处是受控故障下的模型自主原工具接续，不是自然发生故障，也不是 `resume` 收益证据。

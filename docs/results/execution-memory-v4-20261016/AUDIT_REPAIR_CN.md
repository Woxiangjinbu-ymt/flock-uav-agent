# 实验后的审计长度修复

这是一项**不调用模型、不执行工具**的解析修复。三轮 54 次真实实验先按原版完成，原版完整性检查通过，再封存 1,859 个文件；下述修复没有替换原实验统计。

## 修复内容

原提示未声明计划理由的 240 字符上限，真实回复有 7 条理由长 248–325 字符，因此被记为格式无效。当前源码只将 `planned_action.reason` 上限改为 1024；与冻结生产源码比较，这是唯一差异。`observed_change.summary` 的 240 上限、JSON 段 4096 上限、提示、证据规则和工具执行逻辑全部保留。

新增 22 项回归，覆盖长度边界、非法类型、总段长度、真实回复、旧格式及“计划不能变成事实”。修复后的 v4 单元／集成测试与 v3 单元测试共 **108 项通过**。

## 离线回放结果

使用各次实际保存的原始回复和模型调用前上下文，分别运行冻结版与修复版审计，共 **169 次**：

| v4 声明统计 | 实际运行的原版审计 | 修复后离线审计 |
|---|---:|---:|
| 格式有效 | 7 | 14 |
| 格式无效 | 7 | 0 |
| 结构化变化得到支持 | 5 | 12 |
| 结构化变化不受支持 | 2 | 2 |

v4 另有 43 条回复没有声明；未触发要求时不强制声明，也不把缺少声明算成“理由正确”。v2、v3 的审计全部保持不变。

冻结版重放逐条复现了全部原始审计；修复版只有上述 7 条长度失败记录发生变化，其余记录逐字一致。两条变化基准混淆仍判为不支持。格式有效或结构化支持，**都不代表整段自由文本真实，也不代表某次查询是必要的**。

成功率、重复查询、工具调用、token 等行为指标全部沿用原版真实执行。没有重跑模型，没有用修复后的格式有效率替代原版格式失败率。

## 如何核查

- [修复前封存清单](pre-repair-seal.json)：原始场景、源码归档、请求、回复、审计、结果和汇总均保留哈希。
- [原版汇总](summary.json)与[完整性检查](integrity.json)记录修复前已通过的状态。
- [离线回放](audit-replay.json)保留两套审计、7 条差异和输入哈希；回放重新核对 1,859 个封存文件全部不变。
- `experiments/analysis/replay_execution_memory_v4_audit.py` 可重现回放，明确只允许两份当前文件与实验清单不同：生产解析器及新增单元测试。生产差异必须精确等于上述单点长度调整。

当前源码已经包含修复，因此原 runner 的“当前源码等于实验清单”检查会按设计报不一致，不能直接用当前源码重跑旧清单。原实验运行版本仍完整保存在 `experiments/execution-memory-mvp-v4/frozen-source/`，原 manifest 没有重写。原 `integrity.json` 的通过结论表示**修复前检查时**一致；修复后归档与原始结果的完整性由单独回放记录确认。

# Memory 第五版：保留完成证据，减少完成后的多余动作

日期：2026-10-16。

**这轮在六个场景中取得了较一致的行为改善：三轮都减少了完成后的额外调用，必要步骤没有减少。但还不能说所有场景都更省 token，最终文字也仍有错误。**

## 做了什么

新增有真实回执来源的“已完成／剩余／尚未核实”清单，让模型继续处理原任务里还没完成的要求。

旧账本其实已经保留了到访记录，问题是模型没有始终据此行动。新版明确区分：**访问目标不等于必须定位目标中心**。本人在当前任务中的到访回执，不应被目标对象的 `is_reached=false` 否定；这两个信息在当前实现中并未同步更新。

路线任务则补充了落地判断：航点走完后仍保留落地义务，真正落地后才移入已完成；再次起飞或出现位置矛盾时，不能继续沿用旧的落地证明。未知子句保留待核实，计划和模型自述不算完成证据。

**memory 没有拦截工具，也没有自动结束任务。** 模型选择继续查询时，工具照常执行。原 v4 事实视图和查询说明保持一致，只增加简短的续做清单。

## 怎么验证

以当前 **v4 为基线、v5 为新方案**，原来的 6 个场景各重复 3 轮，共 36 次真实执行。运行顺序和预算提前固定，逐字节复用场景及公开历史，没有挑选重跑，也未扩大到 100 题。

主要统计“**模型已收到整个原任务完成的公开证据后，仍选择的额外工具调用**”。必要落地、失败后的感知重试不算；同一回复预先安排的工具另列。这是本轮具体任务的额外工作指标，不代表能够识别所有无用动作。最终成功由独立任务检查器核查，不把检查器答案提供给模型。

## 结果

| 三轮合计，每版 18 次 | v4 基线 | v5 |
|---|---:|---:|
| 任务达成／正常结束 | 18/18 | 18/18 |
| 已知完成后额外调用 | 7（6次查询、1次动作） | 0 |
| 工具调用 | 41 | 30 |
| 模型调用 | 59 | 48 |
| 同位置重复感知 | 0 | 0 |
| 总 token | 156,313 | 130,631（−16.43%） |

| 轮次 | 完成后额外调用 v4 → v5 | 总 token v4 → v5 |
|---|---:|---:|
| 第一轮 | 3 → 0 | 48,683 → 43,516 |
| 第二轮 | 3 → 0 | 67,568 → 43,513 |
| 第三轮 | 1 → 0 | 40,062 → 43,602 |

18 个配对中，完成后额外调用 **7 次改善、11 次持平、没有增加**。同回复预排的完成后调用、重复已完成子步骤，两组也都是零，不能声称这些指标有所改善。

## 哪些改善比较可靠

- **已完成路线：三轮均有效。** v4 每轮再查一次状态；v5 使用已有完整路线和落地回执，直接报告结果。
- **两个线索任务：避免了三次到访后的查询。** v5 六次都在任务指定的无人机收到本人到访回执后结束，没有借用另一架无人机的完成记录。
- **失败感知：必要重试仍保留。** v5 三轮都重新感知、定位，再移动到目标；其中一轮比 v4 少了访问完成后原指令未要求的落地。
- **两种中断路线：正确续做，但没有减少动作。** 三轮都补完剩余两个航点再落地，没有跳过步骤；新增清单使每次用量增加约 1,900–2,100 token。

人工核对 v5 全部 18 次执行，均有依据停止，没有提前放弃。成功率没有提高，因为基线本轮也全部成功；当前证据主要支持执行效率的局部改善。

## 仍然没有解决什么

**token 节省并不稳定，也不能全归因于完成后去重。** 第三轮 v5 用量反而增加 8.84%。第二轮横向线索中，v4 在完成前多做了四个搜索步骤；这一配对贡献了约 80% 的净 token 降幅。少掉的 11 次工具调用中，7 次是完成后额外调用，另外 4 次是完成前的搜索路线差异。


**最终文字仍需改进。** v5 有 5 条路线回复将着陆前航点 `(140,0,20)` 写成落地位置，实际落地高度为 0。真实执行和停止判断都正确，但不能据此声称结果说明完全准确。

## 下一步

保留“已完成／剩余／尚未核实”的设计，优先压缩尚未完成时重复的清单内容，降低路线场景的提示成本；同时把“历史航点位置”和“落地后的实际状态”分清，改善最终报告。继续以任务完成、额外动作和必要重试为主指标。

这三轮仍是同六个开发场景的重复观察，尚不能说明在独立任务或 100 题上同样有效。

归档日期：2026-10-05，北京时间。离线核验完成于 2026-10-05T13:46:19.116994+08:00。

本轮已跑通 MultiUAV-Plat 的数据、Agent、并行仿真、截止控制、原检查评分及证据归档链路，并完成两种模型各 1500 条计划任务的失败计分收束。**“计分收束完成”不等于所有任务都实际执行完，也不等于原 runner 的 `valid_complete_run=true`。** Worker 无法结束而阻断的后续任务纳入失败分母，原始未评分记录保持原样。

## 2 从数据到最终计分的流程

1. 固定 benchmark、75 个场景、原始任务顺序、模型配置、源码与依赖快照。
2. 调度器为场景分配隔离的 Server、Agent 和日志目录；最多同时执行 8 个场景。
3. 载入原环境并建立该 session 的黑板；逐题执行 set-current、落地和充电准备。
4. Agent 接收自然语言指令，经模型调用选择合法感知、导航、覆盖、拍照等工具，与仿真环境交互。8 workers 是实验并发数，不代表单任务采用 8 个相互协作的独立 LLM。
5. Agent 完成或 500 秒到期后，关闭该任务的动作准入，排空已接收请求并暂停环境演化，保存 after、barrier 和 window。
6. 使用原隐藏检查树评估冻结环境，保存逐叶响应和整树通过结果；随后等待 Worker 确认结束，决定是否能安全进入下一题。
7. 本报告保留已经形成的原检查结果；执行中断后未评分的后续题按失败补齐计分分母。首次执行口径不整场重跑，不拼接不同代次的最好结果。

检查树包含 AND、OR 和反向期望；原数据有 26 条任务包含 OR。Task Pass 使用原树返回值，不能用“所有叶子为真”替代。已有动作窗口结束后不再允许模型获得额外动作预算；排空、检查及清理耗时仍计入墙钟成本。

## 3 为什么未封存，以及本次怎样计失败

这不是已完成结果在磁盘中丢失。runner 在等待 Worker 退出之前已经保存环境与评分；如果 Worker 在额外等待 120 秒后仍未确认结束，runner 为避免旧线程污染下一题而停止该场景，因此后续任务没有执行。作业状态 cancelled 只是取消标记，不能证明执行线程已返回。

本轮进一步核对发现：Qwen 首次执行的 **13 个 Worker 未退出案例均有 1 个 HTTP 请求开始事件，而没有对应结束或错误事件**。取消在模型/工具回调边界检查，不能保证即时打断一个尚未返回的同步请求。这支持“未返回的模型请求阻碍协作式取消”的解释；遥测不能进一步判定是服务端推理、网络等待还是客户端阻塞，也不能据此断言模型规划错误。证据见 worker-stop-evidence.json。

| 对象 | 首次执行中已评分 | 因执行停止而未评分 | 其他独立问题 |
|---|---|---|---|
| DeepSeek | 1483 / 1500 | 17 任务 / 144 检查；1 个场景 | 37 个任务发生终止性模型服务错误：36 个 HTTP 402，1 个最终 HTTP 429 |
| Qwen | 1444 / 1500 | 56 任务 / 587 检查；13 个场景发生 Worker 未退出 | 首轮没有终止性 API 错误；13 个未结束请求单列 |

DeepSeek 的 17 条缺口来自 `Unexpected/cancelled job; cannot assume execution has stopped`，与 Qwen 的 `Worker did not exit` 不是同一个错误字符串，但同属无法确认安全继续执行；本报告分别保留原因。DeepSeek 37 个服务失败任务中有 12 个原检查通过，说明继承的环境状态可能满足检查；部署口径将这些服务执行失败任务记零，其原检查响应仍保留。

| 情况 | Task Pass 与检查分 | 严格部署成功 |
|---|---|---|
| 正常完成并有检查 | 保留原检查树与逐叶结果 | 检查通过且 Worker 确认退出时成功 |
| 500 秒超时，但环境已冻结且已有检查 | 保留原检查，不自动全零 | 检查通过且 Worker 确认退出时成功 |
| 环境已冻结、检查已保存，但 Worker 未结束 | 保留原检查与部分分数 | 失败；即使环境检查通过也不算可靠收尾 |
| 上述中断导致后续任务未执行或未评分 | 任务失败；计分贡献为 0，保留全部任务和检查分母 | 失败 |
| 终止性模型服务错误 | 首次部署口径任务与检查贡献为 0；保留原观察值 | 失败，另标服务故障，不称模型能力失败 |

补零只发生在派生结果的 credited_checks、task_pass 等字段。原始 leaves、status=not_run/invalid、原日志和封存文件没有被改成伪造的实测失败。`accounting_complete=true` 表示 1500 个计划任务都有明确计分归属；原 runner 的有效完成标志保持不变。

本次协议变更发生在观察结果之后，应作为事后审计披露，不能声称事前注册。后续对照与消融需在运行前固定同一失败规则，禁止通过事后挑选口径制造改进。

| 统计口径 | DeepSeek Task Pass | Qwen Task Pass | 适用解释 |

口径 B/C 的 DeepSeek 保留 6 个明确服务故障场景的既有修复版本，但撤回了 `ae503ad1` 运行中断场景的补跑收益：保留首次已完成的 3 条，后续 17 条失败。历史 1283 次成功变为 1268 次，减少 15 次成功，**85.53% → 84.53%**。再完全撤回 6 个服务场景补跑，并将首次 37 个服务失败任务记零，得到主表 1243 次成功、82.87%。

口径 C 的 Qwen 固定使用第三次补跑启动前的完整快照：68 个封存场景加 7 个 generation 3 中断场景；1482 条已有评分、18 条执行缺口记失败，得到 **1163/1500 = 77.53%**，Avg. Check **87.03%**、Global Check **80.69%**、Total Failed **5.80%**。未根据后续 generation 4 的任务成败挑选结果。首次部署则统一回到所有场景 generation 1，56 条缺口全部记失败。

因此不能只把最后剩下的 18 条补零，就称它为“从未重跑”的实验。C 是已经发生恢复的工程收束结果；A 才对应取消整场恢复收益的部署问题。若后续论文主要研究 Agent 算法，可同时报告 A 与 B，并固定基础设施异常处理规则；不能只挑更有利的一个。

## 7 初步失败案例分析

以下案例按原始首次执行证据核对；机制分析是代表性证据，不把所有失败自动归入单一根因。先区分运行可靠性、规划执行、验证语义与数据规格，后续局部修复始终应占用同一 500 秒预算。

| 类型与任务 | 观察结果 | 解释与可研究方向 |
|---|---|---|
| Worker 长尾未退出；79b207ff/9349f4d1 | Qwen 原检查 0/20，随后 5 条任务未执行 | 最后一个模型 HTTP 请求约在动作窗口第 194 秒开始，未见结束回执；截止、评分与退出是三个不同阶段。需研究请求截止与执行器取消，不是反复重跑求通过 |

## 8 与原论文的关系及下一步

已重新读取本地归档论文第 10 页表 4。原论文 Agent4Drone + deepseek-flash 为 Task Pass 69.60%、Avg. Check 83.40%、Global Check 80.76%；它不是当前官方 deepseek-flash 服务别名或 Qwen3.8 Flash。当前主表使用部署失败追加计分，模型、接口适配及故障处理不同。因此本次是**在原平台与任务上建立当前模型 baseline**，不能声称严格复现了历史模型数值，也不能由本轮更高/更低的数值证明原论文结果可靠或不可靠。

已有证据能确认：平台链路可运行、原检查可离线重放、当前模型可区分表现，Target Assignment 与长序列任务仍有明显失败空间。当前还缺同一协议下的多次独立重复、稳定的供应商故障条件、ReAct 对照与模块消融，因此没有足够证据把模型差异归因于某个方法模块。

下一阶段先冻结 no-scene-replay 规则与服务故障处理，再独立实现预算内取消、执行条件验证和局部修复。先用固定开发子集验证机制和成本；正式方法与消融使用相同 1500 任务、原顺序、500 秒、8 workers 和模型配置，并同时报告任务成功、可靠收尾、检查部分分、调用时延及全部实际开销。需要改导航契约、重置语义或检查定义时另设修正版协议，不改写本报告历史记录。
